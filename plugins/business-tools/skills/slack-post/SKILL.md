# Slack Post

Slack 投稿文を作るときの規範。
プラットフォーム制約（後から直せない・流し読みされる）を前提に、投稿前に完成形へ整える。
伝わるかどうかの責任は、受け手の察しではなく送り手の明示に置く。
簡潔にするとは短くすることではなく、受け手の判断に要る情報だけを残すことを指す。

## プラットフォーム制約（前提知識）

- **bot / API 経由の投稿は、投稿後に人間が編集・削除できない**。投稿前にフォーマットを完成させる
- Slack の見出し記法はない。`*太字*` をセクション見出しとして使う
- 長文は自動で折りたたまれる。結論は冒頭3行以内に置く
- コードやログは必ずコードブロックに入れる

## フォーマット規則

- セクション見出し（`*1. xxx*` など）の**前後に空行**を入れる
- 段落ごとに改行を挟む
- 箇条書きは1項目1行。ネストは1段まで。同じ階層には同じ粒度の情報を置く
- 1行を短くし、縦に読める形にする
- 絵文字は文頭の識別用に最小限

## 文章規則（ローコンテキスト）

- 一文15語未満を目安に短く切る。一文に主張は一つ
- 主語・動詞・目的語を明確にし、能動態で書く
- 形容詞・曖昧語（「遅い」「多い」「ほぼ」「少し」）と弱い表現（「できれば」「なるべく」）は、期間・件数・割合・日時に置き換える。元の情報に数値が無ければ言葉を残し、仮定の一覧に挙げる
- 略語・専門用語は初見の人に通じる言葉を選ぶ。避けられない場合は括弧で展開
- 同じものは同じ言葉で呼ぶ
- 人によって指す範囲が変わる言葉（予算、リスク、マネジメントなど）は、初出でどの意味かを添える
- 書いた文に「So What?」と自問し、答えがない文は削る

## 冒頭の1行

新規の投稿では、冒頭の太字の1行で、投稿の形式と受け手に求める反応を伝える。
形は `*形式: 結論の句（期限、求める反応、対応不要のどれか）*` にする（`*相談: リリースを延期（判断の期限10/14 17:00）*`）。
本文の1行目は形式を繰り返さず、結論の文から始める。
太字の行に収まらない期待値（頭出しか今回で決めたいか、投稿の全体に当てはまる確実性、一部の人にだけ求める反応）は、結論の文の次の行に書く。
スレッドでの返信には太字の行を置かない。依頼への返信は、受領と次に返す日時の文から始める。
書かないと、共有のつもりの投稿に受け手が助言や判断を返そうとする。

- 形式 — 依頼 / 相談 / 意見の収集 / 壁打ち / 報告 / 共有 / 案内 / 雑談 のどれかを書く。型の例もこの語を使う。相談なら、頭出しなのか今回で決めたいのかも書く
- 求める反応 — 読むだけか、意見か、判断か。意見なら種類も書く（途中の案を広げる意見か、仕上げた案の欠点の指摘か）
- 確実性 — 確定したこと、検討を終えた案、今思いついた案、整理できていない考え、立証できない主観、確証のない仮説、人から聞いた話（出どころを添える）を区別する。指摘を避ける予防線としては書かない。投稿の全体に当てはまるなら結論の文の次の行に、一部だけならその行か欄の見出しに書く
- 所要時間 — 要るときだけ書き、実際の分量と合わせる

載せるかどうかは「載せる情報を選ぶ」で先に決め、確実性は載せると決めた情報にだけ付ける。
形式と期待値は1行に収める。配慮の言葉を足すなら別に1文までにし、その直後に結論を書く。

## 本文の組み立て

- 結論、理由、判断に要る詳細、次のアクションの順に置く。起きた順に書かない。経緯は求められたときにスレッドで足す
- 悪い知らせは結論の文に含める。別の文になるなら、結論の直後の文に書く
- 確認した事実、そこからの解釈、これから行う対応を別の行に分ける。解釈を事実の形で断定しない
- 理由は受け手の判断を左右する順に並べ、2〜3点に絞る
- 結論が出ていないなら作らない。「現時点では判断できない」と最初に書き、分かっていること、これから確認すること、いつ結論を出すかを分ける
- 質問に答えられないときは「分かりません」だけで返さない。把握していることと把握していないことを分け、次にできることを添える（「商談があったことは把握していますが、結果は未確認です。担当に聞いて15:00までに返します」）
- 受け手が次に何をするか（判断する、返信する、対応不要）を書く

## 載せる情報を選ぶ

- 受け手がこの投稿を読んで何を決めるのかを先に固定する
- 受け手が知らない前提（背景、関係者、用語）は補い、すでに伝えた内容は繰り返さない
- 受け手の判断を変えない情報と、後から確認できる情報は、スレッドの返信かリンクへ回す
- 数値の精度は判断に要る水準で選ぶ。規模感で足りるなら「約1万件」、契約金額、障害件数、法的な要件は正確な値を書く
- 受け手が聞きそうな質問を投稿の前に挙げ、判断に関わるものは本文で先に答える。全部を網羅しない
- やり取りの少ない相手には、推測を混ぜず事実で書き、投稿の意図を省かない。目的、内容、期限、方法を1つずつ書く
- 受け手の立場で優先する情報を変える

| 受け手 | 優先する情報 |
| --- | --- |
| 経営者 | 経営判断に使う数値、リスク、影響 |
| 部門やチームの責任者 | 見込み、進捗、課題、全体への影響 |
| 現場の担当者 | 実施内容、具体的な手順 |
| 他部署 | 相手の部署との関係、必要な協力 |

## 往復を減らす

Slack は相手がいつ読むか分からない。往復が1回増えるたびに、判断と作業が遅れる。

- 相手が次に聞くことを先に書く。日程の調整は「空いていますか」と聞かず、用件と候補の時間帯を3つ出す
- 質問は1投稿にまとめる。小出しにしない
- 返信が要るか、急ぎか、いつまでに要るかを書く。急ぎにするのは、返事が無いと次の作業に進めないときと、相手の対応で進め方が大きく変わるときに限る
- 相手が了承する見込みが高く、後から変えられることは、確認を待たずに進めてから報告する（「明日17:00で会議室を押さえました。都合が悪ければ変えます」）。変えられないことと、費用や対外的な約束が絡むことは先に確かめる
- すぐに答えられない質問には、返す時刻を先に返す（「16:00までに返信します」）

## 依頼に含める項目

依頼は次の項目を1投稿で渡す。欠けると、受け手は「正解」を推測して動くことになる。

| 項目 | 書くこと |
| --- | --- |
| 目的・背景 | なぜ今これが必要か。何が困っているか |
| 期待成果 | 何ができていれば終わりか |
| 期限 | 具体的な日時。仮の日付なら仮と書く |
| 担当 | 誰が何をするか。依頼後に自分がすること（確認・共有）も書く |
| 受け入れ基準 | 客観的に判定できる完了条件 |
| 相談先 | 期限や内容で困ったときに、どこへ何を返せばよいか |

- 作業の量が読み取りにくい依頼は、期待する粒度（30分の確認か、数日の作業か）も書く
- 受け手が第三者（取引先など）へ転送しそうな依頼は、社内でしか開けないリンクや社内事情を本文に入れない

## 相談に含める項目

- 最初に、相談で何を得たいかを書く（聞いてほしいだけ / 複数の案から選んでほしい / 助言がほしい）
- 背景、今の状況、目的、制約、自分の考えを先に出す。小出しにしない。判断に要るものだけを選ぶ
- 大枠から問題の箇所へ絞って書く。細部（「メルマガの開封率が」）から始めず、全体のどこで困っているかを先に書く
- 自分の仮説を添える。考えがまとまっていなければ、そう断って壁打ちとして出す

## 場面ごとの追加の規則

次の場面では、書き始める前に該当のファイルを読む。本文の規則はどの場面にも適用する。

| 場面 | 読むファイル |
| --- | --- |
| 依頼への返信、読み取れない投稿への返信、感情的な投稿への返信 | `references/replies.md` |
| 会議の案内、会議のまとめ、通話で決めたことの共有 | `references/meetings.md` と `references/templates.md` |
| 新規の投稿で、依頼、判断を求める相談、進捗の報告に当たるもの | `references/templates.md` |

- Slack のやり取りで論点が収束しないときと、感情が強いやり取りは、同期（通話・会議）へ切り替える案を利用者に出す
- 重要な判断を DM だけで完結させない

## 出力手順

1. 目的（依頼 / 相談 / 報告 / 共有 / 案内 / 返信）、受信者、投稿先（新規の投稿か、スレッドでの返信か）を確認する。形式、求める反応、内容の確実性、受け手が知りたい範囲が分からなければ利用者に聞く
2. 結論を1文で決める。新規の投稿なら、それを10文字前後の句（「リリースを延期」）に縮め、冒頭の太字の行の結論の句にする。10文字は句の部分の目安で、形式と期限は数えない。スレッドでの返信では句を作らない
3. 上の各節の規則で本文を組み、受け手の判断に要らない情報を外す
4. 「場面ごとの追加の規則」の表に当たる場面なら、該当のファイルを読んでから書く。型は依頼 / 判断を求める / 進捗報告 / 依頼への返信 / 会議の案内 / 会議のまとめがある。欄の名前の変更と、欄の追加や削除は内容に合わせて行ってよい
5. 利用者に聞けずに仮定を置いた箇所は、文面とは別に列挙して見せる。担当や期限のように決定として書けない仮定は、文面では相手への打診として書く
6. **投稿見本をそのまま出力し、改行・見た目込みでユーザーに確認してもらう**（承認前に投稿しない）
