# Slack Post

Slack 投稿文を作るときの規範。
プラットフォーム制約（後から直せない・流し読みされる）を前提に、投稿前に完成形へ整える。
伝わるかどうかの責任は、受け手の察しではなく送り手の明示に置く。
簡潔にするとは短くすることではなく、受け手の判断に要る情報だけを残すことを指す。

## プラットフォーム制約（前提知識）

- **bot / API 経由の投稿は、投稿後に人間が編集・削除できない**。投稿前にフォーマットを完成させる
- Slack の見出し記法はない。`*太字*` をセクション見出しとして使う
- 長文は自動で折りたたまれる。結論は冒頭 3 行以内に置く
- コードやログは必ずコードブロックに入れる

## フォーマット規則

- セクション見出し（`*1. xxx*` など）の**前後に空行**を入れる
- 段落ごとに改行を挟む
- 箇条書きは 1 項目 1 行。ネストは 1 段まで
- 絵文字は文頭の識別用に最小限

## 文章規則（ローコンテキスト）

- 一文 15 語未満を目安に短く切る。一文に主張は一つ
- 主語・動詞・目的語を明確にし、能動態で書く
- 形容詞・曖昧語（「遅い」「多い」「ほぼ」「少し」）と弱い表現（「できれば」「なるべく」）は、期間・件数・割合・日時に置き換える
- 略語・専門用語は初見の人に通じる言葉を選ぶ。避けられない場合は括弧で展開
- 同じものは同じ言葉で呼ぶ
- 書いた文に「So What?」と自問し、答えがない文は削る

## 冒頭の 1 行

新規の投稿では、冒頭の太字の 1 行で、投稿の形式と受け手に求める反応を伝える。
形は `*形式: 結論の句（期限か対応不要）*` にする（`*相談: リリースを延期（判断の期限 10/14 17:00）*`）。
本文の 1 行目は形式を繰り返さず、結論の文から始める。
スレッドでの返信には太字の行を置かない。依頼への返信は、受領と次に返す日時の文から始める。
書かないと、共有のつもりの投稿に受け手が助言や判断を返そうとする。

- 形式 — 相談 / 意見の収集 / 壁打ち / 共有（対応不要） / 結果の報告 / 雑談 のどれかを書く。相談なら、頭出しなのか今回で決めたいのかも書く
- 求める反応 — 読むだけか、意見か、判断か。意見なら種類も書く（途中の案を広げる意見か、仕上げた案の欠点の指摘か）
- 確実性 — 確定したこと、検討を終えた案、今思いついた案、整理できていない考え、立証できない主観、確証のない仮説、人から聞いた話（出どころを添える）を区別する。指摘を避ける予防線としては書かない。投稿の全体に当てはまるなら冒頭に、一部だけならその行か欄の見出しに書く
- 所要時間 — 要るときだけ書き、実際の分量と合わせる

載せるかどうかは「載せる情報を選ぶ」で先に決め、確実性は載せると決めた情報にだけ付ける。
形式と期待値は 1 行に収める。配慮の言葉を足すなら別に 1 文までにし、その直後に結論を書く。

## 本文の組み立て

- 結論、理由、判断に要る詳細、次のアクションの順に置く。起きた順に書かない。経緯は求められたときにスレッドで足す
- 悪い知らせほど最初の 1 文に書く
- 確認した事実、そこからの解釈、これから行う対応を別の行に分ける。解釈を事実の形で断定しない
- 理由は受け手の判断を左右する順に並べ、2〜3 点に絞る
- 結論が出ていないなら作らない。「現時点では判断できない」と最初に書き、分かっていること、これから確認すること、いつ結論を出すかを分ける
- 受け手が次に何をするか（判断する、返信する、対応不要）を書く

## 載せる情報を選ぶ

- 受け手がこの投稿を読んで何を決めるのかを先に固定する
- 受け手が知らない前提（背景、関係者、用語）は補い、すでに伝えた内容は繰り返さない
- 受け手の判断を変えない情報と、後から確認できる情報は、スレッドの返信かリンクへ回す
- 数値の精度は判断に要る水準で選ぶ。規模感で足りるなら「約 1 万件」、契約金額、障害件数、法的な要件は正確な値を書く
- 受け手の立場で優先する情報を変える

| 受け手 | 優先する情報 |
| --- | --- |
| 経営者 | 経営判断に使う数値、リスク、影響 |
| 部門やチームの責任者 | 見込み、進捗、課題、全体への影響 |
| 現場の担当者 | 実施内容、具体的な手順 |
| 他部署 | 相手の部署との関係、必要な協力 |

## 依頼に含める項目

依頼は次の項目を 1 投稿で渡す。欠けると、受け手は「正解」を推測して動くことになる。

| 項目 | 書くこと |
| --- | --- |
| 目的・背景 | なぜ今これが必要か。何が困っているか |
| 期待成果 | 何ができていれば終わりか |
| 期限 | 具体的な日時。仮の日付なら仮と書く |
| 担当 | 誰が何をするか。依頼後に自分がすること（確認・共有）も書く |
| 受け入れ基準 | 客観的に判定できる完了条件 |
| 相談先 | 期限や内容で困ったときに、どこへ何を返せばよいか |

- 作業の量が読み取りにくい依頼は、期待する粒度（30 分の確認か、数日の作業か）も書く
- 受け手が第三者（取引先など）へ転送しそうな依頼は、社内でしか開けないリンクや社内事情を本文に入れない

## 依頼を受けたときの返信

依頼主が最初に知りたいのは作業の完了ではなく、依頼が受け取られたかどうかである。

- 作業が数時間以上かかるなら、完了を待たずに返す。受領に、着手の時期と次に返す日時を添える
- 返答が要る依頼にスタンプだけで返さない
- 「了解しました」だけで返さない。次の 5 つをどう理解したかを自分の言葉で書く

| 項目 | 確かめること |
| --- | --- |
| 何を | 作業の具体的な内容 |
| 誰が | 担当と役割の分担 |
| どれくらい | 求められる完成度と品質 |
| いつまでに | 納期と、途中で見せる時期 |
| 目的 | 作業の狙い。仮説を添えて確かめる（「狙いは○○で合っていますか」） |

- 細部を質問する前に、依頼の全体をどう理解したかを 1 文で書いて確かめる（「○○の話と理解しました」）。全体が合ってから、足りない点だけを聞く
- 質問は作業を進めるのに要るものに絞る。気になっただけの点は聞かない
- 完成度と期限は組にして書く（「明日までに 2 割の素案」「期日の 3 日前までに 8 割」）
- 推測した部分は前提にせず、仮説として書いて確かめる
- 相対的な言葉は数字や基準に直して確かめる（「なるはや」→「今日中でよいですか」、「いい感じに」→「前回の資料と同じ形でよいですか」）
- 不安な点は引き受ける時点で書く。「できません」だけで返さず、素案を早く出して見てもらう進め方を提案する
- 口頭で合意した内容は、チャットに文章で残す

## 読み取れない投稿への返信

相手の投稿が読み取れないときは、全部を説明し直してもらわない。読み取れた部分を自分の言葉で書き、足りない点だけを聞く。

| 読み取れない原因 | 返信で確かめること | 書き方の例 |
| --- | --- | --- |
| 目的が分からない | 何のための投稿か | 「○○についての相談と理解しました。合っていますか」 |
| 範囲が分からない | どこまでを扱うか、どの深さか | 「頭出しですか。それとも今回で決めますか」 |
| 細部が続いて結論が見えない | 結論か論点 | 「先に結論だけ教えてください」 |
| 事実と解釈が混ざっている | どこまでが確認した事実か | 「△△は確認した事実ですか。そこからの見立てはどうですか」 |
| 長くて要点が拾えない | 自分の理解の要約が合っているか | 「□□と読みました。違う点を教えてください」 |

- 質問は相手の書き方の指摘にしない。自分が何を理解したくて聞くのかを書く
- スレッドが論点から外れたら、元の論点を 1 文で書いて戻す（「先に○○を決めてもよいですか」）
- 相手の発言が多少ずれていても、結論に影響しないなら直さない

## 非同期で収束しないとき

- Slack のやり取りで論点が収束しないときは、同期（通話・会議）へ切り替える
- 同期で決めたことは、決まったこと、次のアクション（誰が、いつまでに、何を）、決まらなかったことの順にスレッドへ戻す。担当か期限が曖昧なら、投稿の前に確かめる
- 決まらなかったことは決まったことと分け、決まらなかった理由、次に要る情報、誰が確かめるか、いつ再検討するかを書く
- 重要な判断を DM だけで完結させない

## 出力手順

1. 目的（報告 / 依頼 / 依頼への返信 / アナウンス / 質問）、受信者、投稿先を確認する。形式、求める反応、内容の確実性、受け手が知りたい範囲が分からなければ利用者に聞く
2. 結論を 1 文で決める。それを 10 文字前後の句（「リリースを延期」）に縮め、冒頭の太字の行の結論の句にする。10 文字は句の部分の目安で、形式と期限は数えない
3. 上の各節の規則で本文を組み、受け手の判断に要らない情報を外す
4. 型が要るときは `references/templates.md` から選ぶ（依頼 / 判断を求める / 進捗報告 / 依頼への返信 / 会議のまとめ）。欄の名前は内容に合わせて変えてよい
5. 利用者に聞けずに仮定を置いた箇所は、文面とは別に列挙して見せる
6. **投稿見本をそのまま出力し、改行・見た目込みでユーザーに確認してもらう**（承認前に投稿しない）
