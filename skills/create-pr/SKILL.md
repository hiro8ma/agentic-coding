# PR の作成と更新

レビュアーが判断するために必要な情報だけを、変更内容から順に書く
本文構成と簡潔さの判断は、Claude Code と Codex が共通で読むユーザールール（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`）を正本とする

- 最新の本文と差分を基準にし、判断に必要な要件 / 関連 PR / 検証結果を確認する
- 会話やリンク先を読まなくても、この PR 単体の変更を理解できるようにする
- 移行番号 / Issue ID / 社内のロール名などだけで説明しない。出すときは、それが何をしたものかを同じ文で書く
- 設定 / 画面 / 業務用語を説明するときは、ユーザールールの「設定や仕組みは、読者に欠けた前提から書く」に従う
- 経緯 / 作業ログ / 自明な実装詳細 / 重複した説明は削る
- 判断に必要な理由 / 適用条件 / 失敗時の挙動 / 制約 / 未確認事項は残す
- 複数の目的が混ざって説明が長くなる場合は、PR 分割を検討する

## タイトル

`{対象}の{何を}{どう変える}` を一文で書く
「対応する」「改善する」「修正する」だけで終わらせず、変更後の状態を示す
接頭辞 / Issue ID / 文字数はリポジトリの規約に従う
Issue ID が必要な場合は `type(scope): ISSUE-ID: {対象}の{何を}{どう変える}` とする

## 本文

ユーザールールやリポジトリが必須とする構成を守る
行数を埋めるために説明を足さない

| 見出し | 内容 |
| --- | --- |
| `## TL;DR` | 変更後の状態を 1 行で示し、重複しない要点を箇条書きで続ける |
| `## 全体像` | 必ず Mermaid を書き、現在 PR をハイライトする。関連 PR があればチェックボックス一覧も添える |
| `## Overview` | この PR の挙動 / 条件 / 例外 / 理由。挙動が変わる場合は before / after の表を置き、同じ内容を繰り返さない |
| `## Reference` | 判断の根拠となる Issue / Notion / Slack などをタイトル付きリンクで示す |
| `## Debug List` | 主要な手動確認と判断に関わる未確認事項をチェックボックスで分ける。`control / variation` の表は、画像や実際の出力で埋められるときだけ置く。埋められないときは表ごと削除し、空の枠を残さない |
| `## Review Deadline` | 具体的な日時を書く。急ぎでない場合はその旨を書く |

TL;DR に実装方法や検証結果は書かず、他 PR との関係は全体像にまとめる
全体像は省略しない。単独 PR では今回の変更の流れを Mermaid で示す
全体像では「この PR」の直後に、今回と直接関係する後続作業をチェックボックスで並べる
後続作業には対応先のタイトル付きリンクと、対応時期または着手条件を添える。未定のものは未定と書く
Overview には今回含める範囲を書く。今回に含まれると誤解されそうな作業だけ、スコープ外とする理由も短く添える
後続作業の順序 / 時期 / リンクは全体像にまとめ、Overview で繰り返さない
Overview のレビュー観点はユーザールールに従い、`#### レビューで特に見てほしい点` に書く
通常の test / lint / build の成功は Checks で確認できれば再掲しない
失敗 / 未実行 / Checks に含まれない重要な検証は、判断に必要な範囲で書く

## 作成と更新

作成前に対象ブランチ / マージ先 / 差分 / 必須チェック / 既存 PR を確認する
新規作成はドラフトを基本とし、提示 / 承認 / Assignee はユーザーとリポジトリの規約に従う
同じブランチの PR は重複作成せず、更新依頼の範囲で最新の実装と検証結果に合わせて整理する
書き込み直前にタイトルと本文を再取得し、他の編集を取り込む
本文は `--body-file` で渡し、反映結果を確認してタイトル付きの PR リンクを返す
コード変更 / コメント投稿 / Ready 化 / マージは行わない

## 最終確認

- タイトルと TL;DR だけで何が変わるか分かるか
- 他 PR を読まなくても、この PR 単体をレビューできるか
- 削っても判断が変わらない行が残っていないか
