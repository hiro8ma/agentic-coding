# 返信の規則

相手の投稿に返信するときに読む。場面に合う節だけを使う。

## 依頼を受けたときの返信

依頼主が最初に知りたいのは作業の完了ではなく、依頼が受け取られたかどうかである。

- 作業が数時間以上かかるなら、完了を待たずに返す。受領に、着手の時期と次に返す日時を添える
- 返答が要る依頼にスタンプだけで返さない
- 「了解しました」だけで返さない。次の5つをどう理解したかを自分の言葉で書く

| 項目 | 確かめること |
| --- | --- |
| 何を | 作業の具体的な内容 |
| 誰が | 担当と役割の分担 |
| どれくらい | 求められる完成度と品質 |
| いつまでに | 納期と、途中で見せる時期 |
| 目的 | 作業の狙い。仮説を添えて確かめる（「狙いは○○で合っていますか」） |

- 受領と日時の文の次に、依頼の全体をどう理解したかを1文で書く（「○○の話と理解しました」）。5つの項目はその後に並べ、質問は足りない点だけにする
- 質問は作業を進めるのに要るものに絞る。気になっただけの点は聞かない
- 完成度と期限は組にして書く（「明日までに2割の素案」「期日の3日前までに8割」）
- 推測した部分は前提にせず、仮説として書いて確かめる
- 相対的な言葉は数字や基準に直して確かめる（「なるはや」→「今日中でよいですか」、「いい感じに」→「前回の資料と同じ形でよいですか」）
- 不安な点は引き受ける時点で書く。「できません」だけで返さず、素案を早く出して見てもらう進め方を提案する
- 口頭で合意した内容は、チャットに文章で残す

## 読み取れない投稿への返信

相手の投稿が読み取れないときは、全部を説明し直してもらわない。読み取れた部分を自分の言葉で書き、足りない点だけを聞く。

| 読み取れない原因 | 返信で確かめること | 書き方の例 |
| --- | --- | --- |
| 目的が分からない | 何のための投稿か | 「○○についての相談と理解しました。合っていますか」 |
| 範囲が分からない | どこまでを扱うか、どの深さか | 「頭出しですか。それとも今回で決めますか」 |
| 細部が続いて結論が見えない | 結論か論点 | 「先に結論だけ教えてください」 |
| 事実と解釈が混ざっている | どこまでが確認した事実か | 「△△は確認した事実ですか。そこからの見立てはどうですか」 |
| 長くて要点が拾えない | 自分の理解の要約が合っているか | 「□□と読みました。違う点を教えてください」 |

- 質問は相手の書き方の指摘にしない。自分が何を理解したくて聞くのかを書く
- スレッドが論点から外れたら、元の論点を1文で書いて戻す（「先に○○を決めてもよいですか」）
- 相手の発言が多少ずれていても、結論に影響しないなら直さない

## 感情的な投稿への返信

相手の感情が誰に向いているかで返し方を変える。自分と第三者の両方に向いているときは、自分に向いているときの手順を主にする。
この節は、SKILL.md の書き出しと並び順の規則（結論を先に書く、返す時刻を先に返す、依頼への返信の書き出し）より優先する。最初の文は今の状態の事実（「まだ出していません」）にとどめ、対応と日時は相手の言い分を整理した後に書く。

- 自分に向いているとき — すぐに反論や解決策を返さない。相手の言い分を、正しいかどうかの評価を加えずに整理して返す。解決策は、相手の言い分を受け取ったと伝えた後に出す
- 第三者に向いているとき — 同意も否定もしない。誰が何をしたかを確かめ、起きたことと相手の評価を分けて返す（「△△が起きた、という事実と理解しました」「□□は○○さんの受け止めですね」）
- 事実と違う言葉（「毎回」など）は文面で訂正しない。整理して返すときはその言葉を写さず、利用者に付記で知らせる
- 自分の側の事情は、相手の言い分の整理の後に事実だけを書く。自分の落ち度は、事実に限って1文で詫びる
- どちらの場合も、感情が強いやり取りは Slack で続けず、通話に切り替える案を利用者に出す。通話の誘いは文面に入れず、利用者が選べるように別に示す
