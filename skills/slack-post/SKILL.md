# Slack Post

Slack 投稿文を作るときの規範。
プラットフォーム制約（後から直せない・流し読みされる）を前提に、投稿前に完成形へ整える。
伝わるかどうかの責任は、受け手の察しではなく送り手の明示に置く。

## プラットフォーム制約（前提知識）

- **bot / API 経由の投稿は、投稿後に人間が編集・削除できない**。投稿前にフォーマットを完成させる。「あとで直す」は存在しない
- Slack の見出し記法はない。`*太字*` をセクション見出しとして使う
- 長文は自動で折りたたまれる。重要な結論は冒頭 3 行以内に置く
- コードやログは必ずコードブロックに入れる（インライン崩れ防止）

## フォーマット規則

- セクション見出し（`*1. xxx*` など）の**前後に空行**を入れる
- 段落ごとに改行を挟み、詰まった印象にしない
- 箇条書きは 1 項目 1 行。ネストは 1 段まで
- 絵文字は文頭の識別用に最小限（乱用しない）

## 文章規則（ローコンテキスト）

- 結論を先に置く。読み手が最初に知るべき So What を冒頭に書く
- 一文 15 語未満を目安に短く切る。一文に主張は一つ
- 主語・動詞・目的語を明確にする（誰が / 何のために / 何をする）
- 能動態を使う。受動態を避ける
- 事実と解釈を分ける。観測した値と自分の判断を同じ文に混ぜない
- 形容詞・曖昧語（「遅い」「多い」「ほぼ」「おおむね」「少し」）は期間・件数・割合などの数字に置き換える
- 弱い表現（「できれば」「たぶん」「なるべく」）で必要条件をぼかさない
- 略語・専門用語は初見の人に通じる言葉を選ぶ。避けられない場合は括弧で展開
- 同じものは同じ言葉で呼ぶ。途中で言い換えない
- 書いた文に「So What?」と自問し、答えがない文は削る
- 受信者の推測に頼らず、額面通りに読める文章にする

## 冒頭で形式と期待値を伝える

冒頭の 1 行で、この投稿の種類と受け手に求める反応を伝える。
受け手はそれを読んで、助言するのか、判断するのか、読むだけでよいのかを決める。
形式を書かないと、共有のつもりの投稿に受け手が助言や判断を返そうとする。

| 形式 | 冒頭の書き方 | 受け手に求めること |
| --- | --- | --- |
| 相談 | 相談です | 意見や助言 |
| 悩みの共有 | 悩んでいます | 状況を聞いてもらう |
| 意見の収集 | 意見をください | 受け手の考え |
| 壁打ち | 壁打ちさせてください | 考えを整理するための対話 |
| 情報共有 | 共有です（対応不要） | 知っておいてもらう |
| 結果報告 | 結果の報告です | 結果の把握 |
| 雑談 | 雑談です | 正式な返答は不要 |

冒頭に足す情報は、次の 5 つから受け手が読む前に知る必要のあるものだけを選ぶ。

- 目的 — 何のための投稿か
- 形式 — 上の表のどれか
- 所要時間 — 読む時間や対応にかかる時間（「2 分で読める相談です」）。通話や会議に誘うときも書く
- 期待する反応 — 読むだけか、意見か、判断か
- 確実性 — 確定したことか、検討を終えた案か、今思いついた考えか、まだ整理できていない考えか

守ること

- 形式と期待値は 1 行に収める。前置きを重ねて本題を遠ざけない
- 書いた所要時間と実際の分量を合わせる。「2 分」と書いて長文を続けない。通話が予定を超えるなら、続けてよいかを相手に確かめる
- 検討を終えた内容と、その場で思いついた内容を同じ調子で書かない
- 相談か共有かを書かずに、受け手に読み取らせない

確実性の書き分け

| 内容の状態 | 冒頭の書き方 |
| --- | --- |
| 答えが決まっていて即答できる | 結論は決まっています |
| ほぼ間違いないと確信している | 確度は高いです |
| 以前に検討したことがある | 以前検討した内容です |
| 今思いついた | 今思いついた案です |
| 考えが整理できていない | 考えながら書いています |
| 強く思うが立証できない | 主観です |
| 正しいと思うが確証がない | 仮説です |
| 言いたいことはあるが言葉が定まらない | うまく言葉にできていません |
| 反論が出ると分かっている | まず最後まで読んでください |
| 自分の意見ではなく人から聞いた話 | 聞いた話です（出どころを添える） |

- 確実性の断りは、内容の状態を正しく伝えるために書く。指摘を避けるための予防線として書かない
- 求める意見の種類を書く。途中の案なら「案を広げる意見がほしい」、仕上げた案なら「欠点を厳しく指摘してほしい」と書く。書かないと、途中の案に完成度の評価が返ってくる

## 載せる情報を選ぶ

簡潔にするとは短くすることではなく、受け手の判断に要る情報だけを残すことを指す。
全部の経緯を書くと、受け手が自分で整理し直すことになり、結論が埋もれる。

- 受け手がこの投稿を読んで何を決めるのかを先に固定する
- 受け手が知らない前提（案件の背景、関係者、用語）は補い、前回の報告で伝えた内容は繰り返さない
- 各情報を次の基準で選ぶ
  - 受け手がすでに知っているか
  - 受け手の判断に要るか
  - 結論の理解に欠かせないか
  - 今伝える必要があるか
  - 後から確認できるか
- 判断に要らないが参照されうる情報は、スレッドの返信かリンクへ回す
- 受け手の立場で優先する情報を変える

| 受け手 | 優先する情報 |
| --- | --- |
| 経営者 | 経営判断に使う数値、リスク、影響 |
| 部門やチームの責任者 | 見込み、進捗、課題、全体への影響 |
| 現場の担当者 | 実施内容、具体的な手順 |
| 他部署 | 相手の部署との関係、必要な協力 |

- 受け手がどこまで知りたいかを推測で決めきれないときは、利用者に確認する。利用者が受け手本人に聞ける場面なら、「結論だけでよいか」「追加で要る情報はあるか」と聞く案を出す

## 悪い知らせと前置き

- 悪い知らせほど最初の 1 文に書く。結論をぼかすと、報告が遅れたのと同じ結果になる
- 確認した事実、そこからの解釈、これから行う対応を別の行に分ける。解釈を事実の形で断定しない

| 種類 | 例 |
| --- | --- |
| 事実 | 顧客から予算の超過を指摘された |
| 解釈 | 価格が失注の最大の要因だった可能性がある |
| 対応 | 次回は初期の段階で予算の条件を確認する |

- 配慮の言葉は 1 文までにし（形式と期待値を伝える冒頭の 1 行とは別に数える）、その直後に結論を書く。謝罪や感謝を重ねて結論を遠ざけない
- 起きた順や考えた順に書かない。結論、理由、判断に要る詳細の順に置き、経緯は受け手が求めたときにスレッドで足す
- 理由は受け手の判断を左右する順に並べ、2〜3 点に絞る
- 数値の精度は、受け手の判断に要る水準で選ぶ。規模感が分かれば足りる場面では「約 1 万件」と書き、契約金額、障害件数、法的な要件のように値そのものが判断を変える場面では正確な値を書く

## 結論がまだ出ていないとき

- 結論を作らない。「現時点では判断できない」と最初に書く
- 分かっていることと、これから確認することを分ける
- 何を確認したら結論を出すか、いつ出すかを書く

## 依頼に含める項目

依頼は次の項目を 1 投稿で渡す。欠けると、受け手は「正解」を推測して動くことになる。

| 項目 | 書くこと |
| --- | --- |
| 目的・背景 | なぜ今これが必要か。何が困っているか |
| 期待成果 | 何ができていれば終わりか |
| 期限 | 具体的な日時。仮の日付なら仮と書く |
| 担当 | 誰が何をするか。依頼後に自分がすること（確認・共有）も書く |
| 受け入れ基準 | 客観的に判定できる完了条件 |
| 相談先 | 期限や内容で困ったときに、どこへ何を返せばよいか |

- 作業の量が読み取りにくい依頼は、期待する粒度（30 分の確認か、数日の作業か）も書く
- 受け手が第三者（取引先など）へそのまま転送しそうな依頼は、社内でしか開けないリンクや社内事情を本文に入れない。必要なら別の返信で補う
- 情報共有だけの投稿は「対応不要」と明記する

## 依頼を受けたときの返信

返信には 2 つの役割がある。受け取ったことを早く伝えることと、何をいつまでにどの完成度で行うかを依頼主と合わせることである。
依頼主が最初に知りたいのは作業の完了ではなく、依頼が受け取られたかどうかである。

一次返信

- 受け取ったことを返すのと、作業に取りかかるのを分けて考える。作業が数分で終わるなら終えてから返し、数時間かかるなら完了を待たずに返す
- 着手まで時間が空くときも、受け取った時点で返す
- 受領だけを書かない。着手の時期、返答の予定、進捗を共有する時期のうち、分かるものを添える（「確認しました。着手は明日で、金曜までに進捗を共有します」）
- 返答が要る依頼にスタンプだけで返さない。スタンプは、依頼をどう理解しどう対応するかを伝えない。返答が要らない連絡へのリアクションには使ってよい

「了解しました」だけで返さない

- 「了解しました」だけでは、何を、いつまでに、どの方法で、どの完成度で行うのか、目的をどう理解したのかが依頼主に伝わらない
- 不安な点や実行できないおそれのある部分は、引き受ける時点で書く。元気よく了承すると、依頼主の期待が実際の理解度より上がる
- 「できません」だけで返さない。素案を早く出して見てもらう進め方を提案する（「初めての作業なので、明日までに素案を出します。そこで方向を見てください」）

すり合わせる項目

| 項目 | 確かめること |
| --- | --- |
| 何を | 作業の具体的な内容 |
| 誰が | 担当と役割の分担 |
| どれくらい | 求められる完成度と品質 |
| いつまでに | 納期と、途中で見せる時期 |
| 目的 | 作業の狙いと、達成したい状態 |

- 完成度と期限は組にして書く（「明日までに 2 割の素案」「期日の 3 日前までに 8 割」）。完成度の認識を合わせてから期限を決める
- 確かめる順は、作業の内容と納期と品質、自分の実行能力と依頼主の期待の調整、目的の順を基本にする。依頼主が先に目的を話したがるなら、その順に合わせる
- 目的は「目的は何ですか」と聞かず、自分の仮説を添えて確かめる（「狙いは○○で合っていますか」）
- 期間の長い作業ほど、目的を最初に文章で残す

すり合わせの精度を上げる

- 「たぶん○○だろう」と推測した部分は、前提にせず仮説として書いて確かめる
- 依頼主の言葉をそのまま繰り返さない。自分の言葉に置き換えて「こう理解しました」と書く。置き換えられないなら、まだ理解できていない
- 相対的な言葉は数字や基準に直して確かめる

| 依頼の言葉 | 確かめる書き方 |
| --- | --- |
| たくさん | 10 個でよいですか |
| なるはや | 今日中でよいですか |
| いい感じに | 前回の資料と同じ形でよいですか |

- 口頭で合意した内容は、チャットに文章で残す（「文章でも残します。期限は○日、ゴールは△△で合っていますか」）

## 非同期で収束しないとき

- Slack のやり取りで論点が収束しないときは、同期（通話・会議）へ切り替える
- 同期で決めたことは、決定・担当・期限としてスレッドへ戻す
- 重要な判断を DM だけで完結させない。関係者が見られるチャンネルかスレッドに残す

## アンチパターン

- **「いい感じに」「なるべく早く」** — 成果・期限・品質を受け手に推測させる
- **長文だが結論がない** — 情報量で明確さを代替している
- **「了解しました」だけの返信** — 何をいつまでにどの完成度で行うかが依頼主に伝わらない
- **目的なしで作業だけ頼む** — 受け手が正解を当てにいく作業になる

## 出力手順

1. 目的（報告 / 依頼 / 依頼への返信 / アナウンス / 質問）、受信者、投稿先（チャンネル / スレッド）を確認する。形式、受け手に求める反応、内容の確実性が分からなければ利用者に聞く
2. 結論を 1 文で決めてから書き始める。決まらないなら「結論がまだ出ていないとき」に従う
3. 結論を 10 文字前後の句（「リリースを延期」「計画どおり進行中」）に縮め、冒頭の太字の行に置く。10 文字は目安で、意味が欠けるなら伸ばす
4. 結論を最初の段落に書く
5. 「載せる情報を選ぶ」の基準で、受け手の判断に要らない情報を外す
6. 依頼なら「依頼に含める項目」がそろっているか確かめる。依頼への返信なら「依頼を受けたときの返信」の項目を確かめる
7. 受け手が次に何をするか（判断する、返信する、対応不要）が読み取れるか確かめる
8. 上記規則で整形する
9. **投稿見本をそのまま出力し、改行・見た目込みでユーザーに確認してもらう**（承認前に投稿しない）

## 型（依頼の例）

```
*お願い: ○○の確認（期限: 7/15 12:00）*

△△のため、○○の確認をお願いします。

*背景*

• なぜ今必要か（1〜2 文。リンクがあれば貼る）
• 確認しないと何が困るか

*お願いしたいこと*

1. □□を確認する
2. 問題があれば本スレッドに返信する

*完了後の流れ*

• 確認していただいたら、私が◇◇を進めます
• 結果はこのスレッドで共有します

*相談先*

• 期限で難しければ、このスレッドで教えてください
```

## 型（判断を求める例）

```
*相談: ○○の進め方（判断の期限 7/15 12:00）*

○○は A 案を推奨します。

*理由*

• □□（数値や事実）
• □□

*懸念点*

• △△の場合は◇◇になります

*判断してほしいこと*

• A 案で進めてよいか
```

## 型（進捗報告の例）

```
*報告: ○○の進捗（対応不要）*

○○は予定どおり進んでいます。

*現状*

• 完了 □□
• 未完了 □□

*課題*

• △△（なければ「なし」と書く）

*次のアクション*

• 7/16 までに◇◇を行います
```

## 型（依頼への返信の例）

```
確認しました。着手は 7/14 で、7/16 12:00 までに素案を出します。

*こう理解しました*

• やること　□□を△△の形にまとめる
• 狙い　◇◇の判断に使う（違っていれば教えてください）
• 完成度　7/16 は 3 割の素案、7/18 に 8 割

*確認したいこと*

• 「なるはや」は 7/18 中でよいですか

*不安な点*

• ○○は初めて扱うので、素案の時点で方向を見てください
```
