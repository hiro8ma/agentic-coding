# reader-test — 執筆コンテキストを持たない読者による文書検証

anthropics/skills の doc-coauthoring が持つ Stage 3（読者テスト）を単体スキルとして切り出したもの。
共同執筆のプロセスを経ていない文書（既に書き上がった ADR・README・ナレッジ）にも適用できる。
正典は agentic-coding リポの `skills/reader-test/` で版管理し、`~/.claude/skills/reader-test/` にはそのコピーを置く。

## 原理

執筆者と同じコンテキストを持つレビュアーは、執筆者と同じ盲点を共有する。
だから検証者は、執筆の経緯・会話履歴・リポジトリ知識を一切持たない別プロセスにする。
生成と検証の分離（pptx スキルの QA サブエージェント、webapp-testing の E2E と同じ原則）の文書版。

実測の裏付けがある（Cross-Context Review、arXiv:2603.12123、2026-03）。
注入誤り 150 件の検出率（F1）は、履歴なしの fresh session 28.6%、自己レビュー 24.6%、**親の文脈を渡したサブエージェント 23.8%**。
サブエージェントを使っても親のコンテキストを渡した時点で自己レビュー以下に落ちる。
また同一セッションでレビューを 2 回繰り返しても改善しない（p=0.11）。
効果の源泉は反復ではなくコンテキスト分離そのもの。

## 手順

### 1. 読者プロファイルを確定する

検証の基準になるため、先にユーザーと合意する。

- 誰が読むか（新規メンバー / 他チーム / 経営層 / 外部）
- その読者が持っている前提知識（社内用語は通じるか、技術スタックは既知か）
- 読了後にとるべき行動（承認する / 手順を実行する / 意思決定する）

### 2. サブエージェントに文書だけを渡す

Task ツール（subagent）で検証者を起動する。
**執筆の経緯・このセッションの会話内容・関連ファイルのパスを渡すことは禁止**。
渡してよいのは文書本文と読者プロファイルのみ。

プロンプトテンプレート:

```
あなたはこの文書の想定読者です。プロファイル: {読者プロファイル}
以下の文書を読み、読者として詰まる箇所をすべて挙げてください。

検出対象:
1. 未定義の略語・固有名詞（初出で説明がないもの）
2. 暗黙の前提（読者が知っている保証のない背景知識）
3. 論理の飛躍(前の段落から導けない結論)
4. 手順の再現性(前提環境・事前条件が明記されていない操作)
5. 読了後の行動の不明確さ(結局何をすればよいのか)

各指摘は「行または節の位置 + 詰まった理由 + 修正案」の形式で返してください。
文書に問題がない観点は「問題なし」と明記してください。

--- 文書ここから ---
{文書本文}
--- 文書ここまで ---
```

### 3. 指摘をフィルタして反映する

- 指摘を鵜呑みにしない。欠陥を探せと指示されたレビュアーは、健全な文書からも何かしら報告する（Anthropic のベストプラクティスが明記する adversarial review の注意点）。読者プロファイル上「既知」でよい前提への指摘は棄却する（棄却理由をユーザーに提示）
- 反映は**部分編集**で行う。全体を書き直すとユーザーの表現と過去の推敲が消える
- 反映後、指摘が多かった場合（5 件以上）は再テストを 1 回だけ実施する
- 終了条件は公式 doc-coauthoring と同じ。「読者が質問に安定して正答し、新しいギャップが出なくなったら完成」

## 使いどころの判定

| 文書タイプ | 読者テストの価値 |
|---|---|
| 引き継ぎ資料・オンボーディング | 高。執筆者の暗黙知がそのまま盲点になる |
| ADR・技術選定記録 | 高。決定の背景が執筆者の頭の中に残りがち |
| 汎用知識ベースの紹介文書 | 低。執筆者固有の文脈が少なく盲点が生まれにくい |
| 定型フォーマットの報告書 | 低。フォーマット自体が盲点を防いでいる |

## 併用するスキル

- japanese-tech-writing / cognitive-rhythm-writing — 文体の規範。読者テストは内容の欠落を見るもので、文体は見ない
- doc-coauthoring（公式）— ゼロから書く場合はこちらの 3 ステージに読者テストが含まれる。本スキルは既存文書への単独適用
