# 作り直しの判定条件と昇格の規則を先に決める

AI エージェントでコードを大量に作り直すと、変更の数が人のレビューの能力を超える。
何をもって正しいとするかを先に決めておかないと、あとで「この変更は正しいのか」という議論が蒸し返される。
このスキルは、書き換えを始める前に、判定条件と昇格の規則を決めて文書にする。

出典は Anthropic の「How to prepare for AI-driven code modernization projects」（2026-09-23）と、公開の code modernization プラグイン（`anthropics/claude-plugins-official` の `plugins/code-modernization`）。

## 手順

### 1. 作り直しの種類を決める

| 種類 | 何が変わるか | 判定の重心 |
| --- | --- | --- |
| uplift | 同じ技術のまま版を上げる | 既存のテスト |
| transform | 別の技術に書き換えるが、振る舞いは保つ | 旧版と新版の出力の比較、本番の入力の再生、並行運用 |
| reimagine | 作りも振る舞いも変える | 仕様から書いたテスト |

種類が混ざるなら、区画ごとに分ける。種類を決めないまま始めない。

### 2. 判定条件（certificate）を書く

変更が要件を満たしたと言える、機械で確かめられる条件を並べる。**レビューする人と一緒に書く。**

安い検査を先に、高い検査を後ろに置く。安い検査で落ちた変更に、高い検査の時間を使わない。

| 順 | 検査 | 例 |
| --- | --- | --- |
| 安い | ビルド、型検査、静的解析、セキュリティの検査 | 新しい指摘が出ない |
| 安い | 既存のテスト、新しいテスト、カバレッジ | 全件が通る、カバレッジが合意した値以上 |
| 高い | 旧版と新版の出力の比較（差分テスト） | 同じ入力で出力が一致する。新しい入力も作って比べる |
| 高い | 保存データと通信形式の往復 | 旧版で書いたデータを新版で読める、その逆も |
| 高い | 独立した敵対的レビュー | 書いたときの文脈を持たないエージェントか人が読む |
| 高い | ステージングでの観察 | 決めた期間、後退がない |

判定役が本当に効くかを確かめる。

- わざとコードを 1 行壊し、判定が落ちることを確かめる（落ちなければ、その判定は何も守っていない）
- 優先度の高い業務ルールごとに、そのルールを実行するテストがあるかを確かめる
- 旧版が手元で動かない（メインフレームなど）なら、差分テストができないことを判定の結果に明記する。その区画は「一部しか証明できていない」扱いにする

既存のテストだけに頼らない。LLM によるリファクタリングを差分ファジングで調べた報告では、19〜35% が機能的に等価でなく、そのうち約 21% は既存のテストで検出できなかった（FSE 2026 Companion）。

### 3. 昇格の規則（promotion policy）を書く

判定条件を満たした変更を、どのくらいのレビューで本番に上げるかを決める。

- 変更を、影響の範囲（壊れたときに誰にどれだけ影響するか）とエージェントの確信度で段に分ける
- 段の中身は、組織が既に持っている変更の分類を使う。新しい分類を作らない
- 影響の小さい段は軽いレビュー、決済や認証などの重要な経路は全件を人がレビューする
- 判定条件を満たせない変更は、人のレビューに回す脇道を作る
- **同じ理由の差し戻しが繰り返されたら、1 件ずつ直さず、手順か判定条件の側を直す**
- レビューする人の時間を先に確保する。業務に詳しい人の時間は、確信度の低い判断に集中させる

### 4. 小さな区画で最後まで通す

- 1 つのモジュールか区画で、書き換えから判定、昇格までを通す
- そこで次を測る
  - トークンの使用量（全体の費用はここから外挿し、最低額として扱う）
  - 判定条件を満たした割合
  - レビューで差し戻された割合と、その理由
  - 安いモデルでの再試行の回数（数回の再試行が、上位のモデルでの 1 回より高くつくことがある）
- 判定条件と昇格の規則に自信が持ててから、全体に広げる

### 5. 文書に残す

次を 1 つの文書（例 `MODERNIZATION.md`）にまとめ、利用者の承認を取ってから書き換えを始める。

```markdown
## 種類
（uplift / transform / reimagine と、区画ごとの割り当て）

## 判定条件
（検査の一覧。安い順。各検査の合格の基準と、実行するコマンド）

## 判定役が効くことの確認
（壊したときに落ちることの確認方法。差分テストができない区画）

## 昇格の規則
（段の分け方、段ごとのレビューの深さ、人に回す条件）

## 試験運用の結果
（区画、トークンの使用量、判定条件を満たした割合、差し戻しの理由）
```

終わったあとも、手順、判定条件、昇格の規則、変更の証拠の記録を、次の作り直しで使える資産として残す。

## モデルの使い分け

- 判定条件で完全に検査できる、機械的で量の多い作業は、安いモデルに任せる
- 難しい変換と、敵対的レビューは、上位のモデルに任せる
- 使い分けは、再試行の回数を測ってから決める

## 併用するスキル

- `verify-mechanism` 判定役が本当に効くか（外すと落ちるか）を対照実験で確かめる
- `staged-execution` 本番のデータや設定を書き換える段階では、1 ステップずつ承認を取る
- `reader-test` 判定条件の文書を、書いた文脈を持たない読み手に読ませる
