# セキュリティの 9 カテゴリの確認方法

各カテゴリに、確認内容、確認方法、見落としを書く。
見落としは ADK 2.2.0（Python と Go）と a2a-sdk 0.3.26 で確かめたもの。版が違えば確かめ直す。

## T 脅威モデル

- 確認内容：保護する資産、攻撃者、攻撃の経路、信頼境界が文書になっているか
- 確認方法：資産（個人情報、業務データ、システムの指示、API キー、セッションの State とメモリ）、攻撃者（外部、内部の不正者、ツールの結果に仕込む間接の攻撃者）、経路（利用者の入力、ツールの結果、RAG、A2A、MCP、State）が並んでいるか
- 見落とし：脅威の一覧（OWASP LLM Top 10、Agentic Applications Top 10）は版で番号が変わる。文書に版と公開日を書く

## I 入力の防御

- 確認内容：モデルに渡す前に、指示の上書きを検出しているか。入力の長さに上限があるか。Instruction に守る規則があるか
- 確認方法：before_model の検査が何を見ているか（最後の利用者の発話だけか、文脈の全体か）
- 見落とし
  - 利用者の発話だけを見る検査は、ツールの結果や RAG の文書に仕込まれた指示を通す。O（出力の防御）の after_tool の検査と組にする
  - 形の照合は言い換えを通す

## O 出力の防御

- 確認内容：モデルの出力の機密情報を伏せているか。ツールの結果に仕込まれた指示（間接の注入）を検出しているか
- 確認方法：after_model で個人情報を伏せる処理と、after_tool でツールの結果を検査する処理があるか
- 見落とし
  - 電話番号はハイフン無しの 10 桁と 11 桁も伏せる
  - ADK 本体の Model Armor のプラグインは、ツールの結果を検査しないように見える（コードを読んだだけで未検証）。after_tool は別に書く

## A 認証と認可

- 確認内容：利用者を認証しているか。認証情報をコードに書いていないか
- 確認方法：エージェントの口の前段に認証があるか。ADK の REST の `/run` をそのまま公開していないか
- 見落とし
  - ADK の REST の `/run` は利用者の ID を本文で受けて認証しない
  - 役割や権限を State から読むと、呼び出し元が `state_delta` で自分を admin にできる。役割は認証した前段から取り、context で運ぶ
  - トークンを検証する関数がスコープを確かめているか。署名、宛先、発行者だけでは書き込みを止められない

## P 最小権限

- 確認内容：ツールが最小権限か
- 確認方法：エージェントごとの許可リスト。外部の内容を読むエージェントに、外部へ送るツールや書き込みのツールを持たせていないか
- 見落とし：外部の内容を読むエージェントが送信のツールを持つと、間接の注入で情報を持ち出せる。検出より先にこの組み合わせを無くす

## N A2A

- 確認内容：A2A を使う場合、通信の認証があるか
- 確認方法：サーバーの前段でトークン（と、必要なら mTLS）を検証しているか。全ての口（v1.0 と v0.3 の互換の口）で検証されるか。Agent Card の署名を検証しているか
- 見落とし
  - Agent Card で認証を宣言しても、サーバーは検証しない
  - Agent Card の署名は、検証の関数を渡さなければ検証されない。ADK の `RemoteA2aAgent` は渡さない。検証の鍵をヘッダーの `jku` から取ると、攻撃者の署名が通る
  - mTLS とトークンを両方求めるなら、トークンを証明書に結び付ける（RFC 8705 の `cnf.x5t#S256`）。結び付けないと、盗んだトークンを別の証明書で使える

## K Kill Switch と上限

- 確認内容：緊急停止（全体、エージェント、ツール）、段階的エスカレーション、ツールの実行回数の上限があるか
- 確認方法：止める状態と回数をどこに持つか。確認はどこで走るか
- 見落とし
  - 止める状態をプロセスの変数に持つと、インスタンスが複数あるとき 1 つしか止まらない。共有の保存先から読み、読めなければ止める
  - エスカレーションの利用者の ID を State から読むと、攻撃者が他人を止められる
  - 回数を State に数えると、呼び出し元が 0 に戻せる
  - ループの上限は ADK の既定に任せない（Python の `max_llm_calls` は 500、Go の通常の実行には無い）

## L 監査

- 確認内容：個人情報を伏せた監査ログと、データの保持の方針があるか
- 確認方法：監査がどこに置かれているか。止めた呼び出しも記録されるか。識別の値をどこから取るか
- 見落とし
  - 監査をエージェントのコールバックの後ろに置くと、前のコールバックが止めた呼び出しが記録されない。ランナーのプラグインに置く
  - セッション ID を State から読むと、ADK は State に入れないので常に unknown になる。コールバックの context の `session.id` を使う
  - ADK は既定でプロンプト、応答、ツールの引数を span の属性に入れる。監査ログを伏せても、トレースから漏れる（`ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false`）

## G ガバナンス

- 確認内容：エージェントの利用の方針と、インシデントの対応の手順があるか
- 確認方法：止める手順（K）を実際に試した記録があるか。誰が止める権限を持つか
- 見落とし：手順があっても、試していなければ要改善

## 実行経路とコールバックの並び

教材は 1 つのコールバックの中に、検出、エスカレーション、Kill Switch、監査を並べる。
ADK のコールバックは、最初に結果を返したところで止まり、後ろは走らない。
並びは次を守る。

| 順 | 置き場所 | 中身 | 理由 |
| --- | --- | --- | --- |
| 1 | ランナーのプラグイン | Kill Switch | 何より先に止める |
| 2 | ランナーのプラグイン | 監査（呼び出しの記録） | 後ろで止められた呼び出しも記録する |
| 3 | エージェントのコールバック | 入力の検査、権限、回数の上限 | 止めたら後ろは走らない |
| 4 | after_tool | ツールの結果の検査 | 間接の注入を止める |
| 5 | after_model | 出力の伏せ字 | 利用者に届く前に伏せる |

## フェイルセーフ

ADK の Python では、コールバックが例外を投げると、実行全体が例外で止まり、ツールは動かなかった（既定で止まる側に倒れる）。
教材の「try/except で囲む」は、例外を捕まえて `None` を返すと、確認を飛ばしてツールが動く（fail open）。
囲むなら、捕まえた後に止める応答を返す。
