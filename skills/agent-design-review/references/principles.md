# 設計原則

チェック項目の背景にある 10 の原則。設計の相談を受けたときや、判定の理由を説明するときに使う。
各原則に、設計のときに自問すること、対応するチェック項目、コード例で起きやすい誤りを書く。
誤りは ADK 2.2.0（Python）で動かして確かめたもの。

## 優先度

実装の手間と、減らせるリスクの 2 軸で並べる。

| 優先度 | 原則 |
| --- | --- |
| 最初から入れる（手間が小さく、効果が大きい） | 単一責任、最小権限、フェイルセーフ、冪等性 |
| 計画して投資する（手間も効果も大きい） | 可観測性、評価駆動、疎結合協調、段階的自律性 |
| 余裕があれば | コンテキスト最小化、コスト意識 |

## 原則ごと

### 1. 単一責任

- 問い：Instruction を 1〜2 文で説明できるか。「〜して、〜して、〜する」と 3 つ以上つながるなら分ける
- 項目：A-1、A-6
- 誤り：分けるほど安くなるわけではない。LLM の呼び出しと入力が増える（C-1）。順序が決まっている処理は `SequentialAgent` にし、振り分けを LLM に任せない（A-3）

### 2. 最小権限

- 問い：このツールが無くてもタスクを終えられるか。終えられるなら渡さない
- 項目：S-1、S-6
- 誤り
  - 役割や権限を State から読んで判断すると、呼び出し元が `state_delta`（ランナーの引数、REST の `/run`）で自分を admin にできる。役割は認証した前段から取る
  - 権限の確認をエージェントの `before_tool_callback` に置くと、プラグインのコールバックの後に走る。監査は拒否より前のプラグインに置く

### 3. 冪等性

- 問い：同じ処理を 2 回実行しても、同じ結果になるか
- 項目：O-2、O-3
- 誤り
  - 引数のハッシュを冪等キーにすると、正当な 2 回目（翌週の同じ注文）も重複として弾く。キーは「同じ意図の要求」を表す値（利用者の要求の ID、セッションと呼び出しの組）から作る
  - 探してから入れる書き方は、間に別の呼び出しが来ると 2 件作る。一意の制約で守る

### 4. 可観測性

- 問い：本番の障害を、トレースから再構成できるか
- 項目：O-1、S-5
- 誤り
  - 計測のための値（開始時刻など）を State に置くと、セッションに保存され、モデルへの入力や監査の記録に混ざる。並行する呼び出しどうしで上書きはしない（ADK は呼び出しごとに State の差分を分ける）が、計測の値は State ではなくメモリの変数か span に持つ
  - ADK はツールと LLM の呼び出しの span をすでに出す。同じものを自作のメトリクスで作り直す前に、既存の span と `gen_ai.client.token.usage` で足りるかを見る

### 5. 段階的自律性

- 問い：リスクに応じて人の承認を残しているか
- 項目：S-6、S-7
- 誤り
  - 自律のレベルを State に置くと、原則 2 と同じく呼び出し元が上げられる
  - `before_tool_callback` から `{"action_required": "human_approval"}` を返すだけでは、モデルへのツールの結果になるだけで、承認の流れは始まらない。承認は対話の外に置き、承認者を認証する
  - 「承認率が 95% を超えたら次のレベルへ」は、承認者が確かめずに承認している場合も満たす。却下の率と、承認後に取り消した件数も見る

### 6. コンテキスト最小化

- 問い：Instruction が長すぎないか（目安 500 トークン）。大きな資料を Instruction に詰めていないか
- 項目：A-6、C-3
- 誤り：長さはフレームワークが足す分を含めて測る。Compaction の要約は積み上がる

### 7. 評価駆動

- 問い：実装の前に評価ケースを決めたか（最低 5 件、本番の前に 30 件が目安）
- 項目：Q-1〜Q-5
- 誤り
  - 評価の CLI の終了コードだけで合否を決めない。実行件数と結果を読む
  - ADK の評価セットでは、`intermediate_data`（期待するツールの呼び出し）は `final_response` と同じ階層に置く。`final_response` の中に書くと、EvalSet として読めない
  - 日本語の長い応答（レポートなど）を `final_response` の文面で比べると、ROUGE は数字しか見ない。構造や判定の一致は、独自の採点かツールの軌跡で見る

### 8. 疎結合協調

- 問い：A の内部を変えたら、B も直す必要があるか。あるなら結合が強い
- 項目：A-4、A-5
- 誤り：A2A のリモートを `AgentTool` で包むと、リモートの入力待ちの問いが消える。入力待ちがあるリモートは、別の組み方にする。保存先を共有していれば、A2A で分けても結合は残る

### 9. フェイルセーフ

- 問い：外部サービスが全て落ちたら、LLM が意味の無い出力を返したら、どうなるか。クラッシュか無限ループなら足りない
- 項目：O-3、O-4、S-7
- 誤り
  - HTTP クライアントのタイムアウトは組み込みの `TimeoutError` の子ではないことが多い（`httpx.TimeoutException` は子ではない）。使うクライアントの例外の型で捕まえる
  - Kill Switch を「最優先で確認する」なら、エージェントのコールバックではなくランナーのプラグインに置く。プラグインが先に走る
  - ループの上限は ADK の既定に任せない（Python 500 回、Go は無し）
  - Kill Switch の状態を外部のフラグから読むなら、ツールの呼び出しごとに問い合わせず、短い間だけ手元に持つ。フラグの取得に失敗したときは止める側に倒す

### 10. コスト意識

- 問い：1 件あたりの平均の費用と、月の見込みの費用が予算に収まるか
- 項目：C-1〜C-5
- 誤り
  - `usage_metadata` から費用を計算するとき、プロンプトのトークン数はキャッシュ分を含む。思考のトークンは出力の単価で数える。ストリーミングでは途中の応答にも使用量が付くので、最後の応答だけを数える
  - 費用の上限を State（`cost_limit_usd` など）から読むと、呼び出し元が `state_delta` で上限を上げられる（原則 2 と同じ）。上限は設定かサーバー側で持つ
  - 上限を超えたときに警告を出すだけでは、費用は止まらない。止めるなら、次のモデルの呼び出しを打ち切る
