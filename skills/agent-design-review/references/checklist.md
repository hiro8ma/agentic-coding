# チェック項目の確認方法

各項目に、確認内容、確認方法（コードで何を見るか）、よくある見落としを書く。
見落としは、ADK 2.2.0（Python と Go）で実際に動かして確かめたもの。版が違えば振る舞いが変わりうるので、使っている版で確かめ直す。

## アーキテクチャ

### A-1 単一責任

- 確認内容：各エージェントの責務が 1 つに限られているか
- 確認方法：エージェントごとに `description` と Instruction を読み、責務を 1 文で言えるか。言えなければ要改善
- 見落とし：責務を分けることが、そのまま費用の削減になるわけではない（C-1 を見る）

### A-2 ツールの数

- 確認内容：1 つのエージェントのツールが多すぎないか（教材の目安は 5 個以下）
- 確認方法：`tools=[...]` と MCP のツールセットの数を数える。MCP は `tool_filter` の後の数を見る
- 見落とし：MCP のツールセットは、絞らなければサーバーの全ツールがモデルに渡る

### A-3 オーケストレーション

- 確認内容：Sequential / Parallel / Loop を用途で使い分けているか
- 確認方法：決まった順序の処理を LLM の振り分けでやっていないか。順序が決まっているなら Sequential、独立なら Parallel。入口の振り分けは LLM に任せ、振り分けた後の順序が決まっている処理だけを固定する、という混ざった構成もある
- 注意：台本のモデルのテストは順序を台本で決めてしまうので、LLM が順序を守るかは確かめられない。実際のモデルの評価ケースで確かめる
- 見落とし：リモートのエージェントを `SequentialAgent` に並べると、後ろの段ほど前の全段の出力を連結して受け取る。ほかのチームの段にも前の段の情報が見える

### A-4 疎結合

- 確認内容：エージェント間の依存が A2A か State の経由に限られているか
- 確認方法：エージェントが別のエージェントの内部（関数、モジュール変数）を直接呼んでいないか。エージェントどうしが同じ保存先（DB、ファイル）を直接読み書きしていないか
- 見落とし
  - State の値は A2A のリモートのエージェントには送られない。届くのは会話の履歴だけ
  - A2A のリモートを `AgentTool` で包むと、リモートの入力待ち（input_required）の問いが空の結果になり、答えも渡せない
  - サブエージェントにしても、ADK Python 2.2.0 では入力待ちへの答えがリモートに届かない。入力待ちがあるリモートは、直接呼ぶ経路で確かめる

### A-5 スケーラビリティ

- 確認内容：各エージェントを独立にスケールできるか
- 確認方法：負荷が違うエージェントが同じプロセスに同居していないか。A2A で分けているなら、各サービスのインスタンス数の設定を見る
- 見落とし：マネージドの実行環境（Agent Engine など）にも最小と最大のインスタンス数、同時実行数の設定がある。「設定不要」ではない

### A-6 Instruction の構造

- 確認内容：Instruction が構造化され、長すぎないか（教材の目安は 500 トークン以内）
- 確認方法：本文を見出しや箇条書きで分けているか。長さは、フレームワークが足す分を含めて測る
- 見落とし：ADK は、サブエージェントを持つエージェントの Instruction に、委譲できる相手の一覧と委譲の方法を自動で足す（測った例で約 700 文字）。書いた本文だけを数えると過小になる

## セキュリティ

### S-1 最小権限

- 確認内容：各エージェントに必要最小限のツールだけを渡しているか
- 確認方法：エージェントごとの許可リストがあるか。書き込みや削除のツールを、読むだけのエージェントに渡していないか
- 見落とし
  - 許可と拒否の両方の一覧を持つと、どちらにも無いツールの扱いが決まらない。許可リストだけにする
  - MCP の `tool_filter` はクライアント側の絞り込みで、サーバーの権限は変わらない

### S-2 入力検証

- 確認内容：利用者の入力を検証しているか
- 確認方法：入力の文の検査と、モデルが解釈した後のツールの引数の検査の両方があるか
- 見落とし：金額などの値は、入力の文ではなく、ツールの引数で検査する。文の正規表現は「マイナス 5000 円」「−5,000 円」を取りこぼす

### S-3 Prompt Injection

- 確認内容：指示の上書きの対策（ガードレール）があるか
- 確認方法：入力のガードレールがモデルの手前にあるか。テストがあるか
- 見落とし：台本のモデルで防御をテストするとき、台本が最初から攻撃に従わない作りだと、防御を外してもテストが通る。防御が無ければ失敗する相手でテストする

### S-4 認証情報の管理

- 確認内容：API キーや認証情報をコードに書いていないか
- 確認方法：`git grep` で鍵の形（`AIzaSy`、`AQ.`、`sk-` など）を探す。Secret Manager か環境変数から読んでいるか。テストの fixture にも実の値が無いか
- 見落とし：テストの fixture や `.env.example` に実の値が紛れる

### S-5 データ保護

- 確認内容：機密情報がログやトレースに出ていないか
- 確認方法：ログとトレースの出力を実際に取り、利用者の入力（電話番号などの試験用の値）が出ないかを確かめる
- 見落とし
  - ADK Python 2.2.0 は、既定でプロンプト、応答、ツールの引数を span の属性に入れる。`ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` で止まる。`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` が切り替えるのはログのイベントだけ
  - ADK Go と Genkit Go も、ツールの引数や入出力を span に常に載せる。送る前に除く処理が要る
  - 自作の span の属性に検索語などの入力をそのまま入れると、上の設定をしても漏れる

### S-6 権限制御

- 確認内容：呼び出し元を認証し、書き込みの操作の前に権限を確かめているか
- 確認方法：エージェントの口（A2A、HTTP）の前段に認証があるか。権限の確認がどのコールバックにあるか。監査と権限の確認の並び順
- 見落とし
  - Agent Card で認証の方式を宣言しても、サーバーは検証しない。検証はサーバーの前段に置く。口を足したら（v1.0 と v0.3 の互換の口など）、認証なしで各口を呼び、全て拒否されることを確かめる
  - エージェントのコールバックは並べた順に走り、最初に結果を返したところで止まる。権限の確認の後ろに監査を置くと、拒否した呼び出しが監査に残らない。監査はランナーのプラグインに置く
  - 承認の判断を State や A2A の入力待ちで受けると、申請者が自分で承認できる。承認は対話の外に置き、承認者を認証する
  - 役割、利用者の ID、実行回数を State から読む判断は、呼び出し元が `state_delta` で書き換えられる。利用者の ID はコールバックの context の `user_id`（前段で認証したもの）、回数はサーバー側で数える

### S-7 Kill Switch

- 確認内容：緊急に止める仕組みがあるか
- 確認方法：特定のツールやエージェントを、デプロイし直さずに止められるか（設定の切り替え、許可リストからの除外、トラフィックの遮断）
- 見落とし
  - 止める手順を試したことがなければ要改善
  - 止める状態をプロセスの変数に持つと、インスタンスが複数あるとき 1 つしか止まらない。共有の保存先から読み、短い間だけ手元に持つ
  - 保存先が読めないときに動き続ける作り（fail open）は要改善。止める側に倒す
  - 確認はランナーのプラグインに置く。エージェントのコールバックに置くと、前のコールバックの後になる

### S-8 出力のフィルタリング

- 確認内容：LLM の出力に機密情報が含まれないように確かめているか
- 確認方法：出力のガードレール（個人情報の伏せ字など）があり、テストがあるか
- 見落とし：電話番号はハイフン付きだけでなく、ハイフン無しの 10 桁と 11 桁も伏せる

## 運用

### O-1 可観測性

- 確認内容：トレース、ログ、メトリクスがあるか
- 確認方法：1 つの要求がサービスをまたいで 1 つの trace になるか。ログに trace の ID が入るか。トークンの使用量のメトリクスがあるか
- 見落とし
  - トークンの監視は、キャッシュ、思考、ツールの結果を分けて数える。ADK Python の `gen_ai.client.token.usage` はキャッシュ分を入力に含めたまま分けない
  - Cloud Monitoring のユーザー定義のメトリクスは、1 つの時系列に 5 秒に 1 点まで。要求ごとに書かず、集計してから書く

### O-2 エラーハンドリング

- 確認内容：全てのツールにエラー処理があるか
- 確認方法：ツールが例外を投げずに、失敗の理由を返しているか。モデルがその理由を読んで次の手を選べるか
- 見落とし：捕まえる例外の型を確かめる。ADK の Interactions API の経路の例外は `genai.errors.APIError` の子ではない。a2a-sdk の HTTP のエラーは `A2AClientHTTPError` で、`httpx.HTTPStatusError` では捕まらない

### O-3 フォールバック

- 確認内容：外部サービスの障害時の振る舞いを決めているか
- 確認方法：再試行、代替の経路、利用者への伝え方
- 見落とし
  - Gemini の生成の呼び出しは、Python（ADK の既定）も Go も、既定では再試行しない
  - 429 は `RetryInfo` の待ち時間に従い、日次の上限なら待たずに諦める
  - ストリーミングで一部を返した後の失敗は再試行しない（利用者に二重に届く）

### O-4 ループ防止

- 確認内容：ループを止める仕組みがあるか
- 確認方法：`LoopAgent` の `max_iterations`、モデルの呼び出しの上限、同じツールを同じ引数で呼ぶ回数の上限
- 見落とし
  - ADK に `max_tool_calls` は無い
  - ADK Python の `max_llm_calls` の既定は 500。同じ呼び出しが 500 回続いてから止まる
  - ADK Go 2.2.0 の通常の実行には、モデルの呼び出しの上限が無い
  - A2A でエージェントが呼び合う構成では、呼び出しの経路を運んで循環を止める仕組みが別に要る

### O-5 セッション管理

- 確認内容：本番で永続化されたセッションを使っているか
- 確認方法：`InMemorySessionService` を本番の経路で使っていないか
- 見落とし：同じセッションでは、次のターンは直前に答えたサブエージェントから始まる。振り分けの確認は、シナリオごとにセッションを分けて行う

## コスト

### C-1 モデル選択

- 確認内容：タスクの難しさに合ったモデルを選んでいるか
- 確認方法：エージェントごとのモデルと、その理由
- 見落とし：エージェントを分けると、呼び出しの回数と入力が増えることがある（測った例で、1 つのエージェントに比べ呼び出し 2〜3 回、入力 13〜22 倍）。分ける前後で、1 件あたりの呼び出しと入力を測る

### C-2 キャッシュ

- 確認内容：繰り返しの要求にキャッシュを使っているか
- 確認方法：Context Cache の設定と `min_tokens`。モデルごとの最小トークン数
- 見落とし
  - ADK の Context Cache は Gemini 専用。Claude では使えない
  - 応答そのものをキャッシュするなら、キーに利用者と権限を入れる

### C-3 Compaction

- 確認内容：長い会話の Compaction を設定しているか
- 確認方法：`EventsCompactionConfig` を App に渡しているか。要約器のモデル
- 見落とし：要約は範囲ごとに積み上がり、長い会話では入力が伸び続ける。要約器を渡さなければ本体と同じモデルで要約する

### C-4 コストの上限

- 確認内容：セッションあたりの費用の上限があるか
- 確認方法：トークンの予算の上限と、超えたときの振る舞い
- 見落とし：ループの上限（O-4）が無いと、費用の上限は 1 回の問い合わせの中で破られる

### C-5 コストの監視

- 確認内容：費用をほぼリアルタイムで監視しているか
- 確認方法：モデル別、エージェント別の内訳と、予算に対する割合のアラート
- 見落とし：O-1 と同じ（キャッシュ、思考の分け方、書き込みの制限）

## 品質

### Q-1 評価セット

- 確認内容：評価ケースが十分にあるか（教材の目安は 30 件以上）
- 確認方法：件数に加えて、正常系、異常系、攻撃の割合
- 見落とし：評価の CLI がケースの失敗でも終了コード 0 で終わることがある（ADK の `adk eval`）。CI では結果を読み、実行件数が 0 でないことも確かめる

### Q-2 正常系のテスト

- 確認内容：主要なユースケースのテストがあるか
- 確認方法：台本のモデルで、振り分けとツールの呼び出しの経路を確かめるテストがあるか

### Q-3 異常系のテスト

- 確認内容：エラーのケースのテストがあるか
- 確認方法：ツールの失敗、外部サービスの失敗、不正な引数のテスト

### Q-4 セキュリティのテスト

- S-3 と同じ観点をテストの側から見る。S-3 の見落としを参照

### Q-5 回帰テスト

- 確認内容：過去のバグの回帰テストがあるか
- 確認方法：監視や障害で見つけた失敗が、評価セットやテストのケースになっているか。まだ本番に出ていないなら対象外にしてよい
- 注意：フレームワークの不具合がまだあることを確かめるテスト（「届かない」を固定するテスト）は、回帰テストではない。直した後に「届く」を確かめるテストに置き換える
- 見落とし：日本語の応答の評価に ROUGE を使うと、数字しか比べない。回帰の検知に使わない
