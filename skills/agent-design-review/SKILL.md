# エージェントの設計レビュー

LLM の出力は非決定的で、ツールの選択も確率的に決まる。
そのため信頼性とコストは、実行時ではなく設計の段階で押さえる。
このスキルは、その押さえ方を 29 項目の点検と、本番投入のゲートにする。

## 使う場面と範囲

| 場面 | 見る項目 |
| --- | --- |
| 設計レビュー | 全項目 |
| PR のレビュー | 変更に関係する項目だけ。関係の判断は下の「変更と項目の対応」を使う |
| 本番投入の前 | 全項目 |
| 四半期ごとの定期レビュー | 全項目。前回の結果との差も書く |
| セキュリティレビュー | S-1〜S-8 に加えて、下の「セキュリティを深く見るとき」の 9 カテゴリとシナリオ |

## 手順

1. 対象と影響範囲を書き出す
   - エージェントの一覧（名前、モデル、ツール、サブエージェント、A2A / MCP の接続先）
   - エージェントどうしが共有する保存先（DB、ファイル、キャッシュ）
   - 変更のある場合は、変更したファイルと、そこから呼ばれる範囲
   - テストの実行方法（`Makefile`、`pyproject.toml`、`package.json` を見る）。実行できるならテストを流し、結果を根拠に使う
2. アーキテクチャ（A-1〜A-6）を点検する
3. セキュリティ（S-1〜S-8）を点検する。1 件でも適合でなければ、この時点で本番投入は不可と決まる
   - PR のレビューでは、差し戻しを先に伝えてから残りを見る
   - 設計レビュー、本番投入の前、定期レビューでは、改善計画を出すために残りの観点も最後まで点検する
4. 運用（O-1〜O-5）、コスト（C-1〜C-5）、品質（Q-1〜Q-5）を点検する
5. 本番投入の可否を判定する
6. アンチパターン（`references/anti-patterns.md`）に当たるものがあれば、該当する項目に紐づけて書く

各項目の「何を見れば判定できるか」と「よくある見落とし」は `references/checklist.md` にある。
点検を始める前に読む。
判定の理由を説明するときや、設計の相談を受けたときは、項目の背景にある 10 の原則を `references/principles.md` で引く。
セキュリティの項目を見るときは、`references/threats.md` の信頼境界と脅威の対応表で、漏れている脅威が無いかを確かめる。

## 判定の規則

- 判定は **適合 / 要改善 / 未対応 / 対象外** の 4 つ
  - 適合：仕組みがあり、それが効いていることをコードかテストで確かめた
  - 要改善：仕組みはあるが、足りない、効いていない、または確かめられない。フレームワークの既定値だけに頼っている場合もここに入れる
  - 未対応：仕組みが無い
  - 対象外：その構成では仕組みが要らない。理由を必ず書く（例：Instruction がキャッシュの最小トークン数に届かない、会話が数ターンで終わる、まだ本番に出ていないので障害由来の回帰ケースが無い）。セキュリティの項目には使わない
- 根拠を必ず書く。ファイルと行（`path:line`）、テスト名、設定の値のどれか
- 根拠を示せないものは適合にしない。「未確認」と書いて要改善にする
- 数値の目安（ツール 5 個、Instruction 500 トークン、評価 30 件）は目安であり、超えていることだけで要改善にしない。超えている理由が妥当かを書く
- 既定値に頼っている項目は、その既定値が何かを書く。主な既定値は `references/checklist.md` の「既定値の早見」にある

## セキュリティを深く見るとき

エージェントの防御は、コードを読むだけでは効いているか分からない。
コールバックの並び、State の扱い、フレームワークの既定値で、あるはずの防御が素通りになることが多い。
そのため、9 カテゴリの点検（`references/security-categories.md`）に加えて、攻撃のシナリオを流す（`references/security-scenarios.md`）。

1. 脅威モデルを確かめる。無ければ、保護する資産、攻撃者、攻撃の経路、信頼境界を 1 枚に書き出す（`references/threats.md`）
2. 実行経路を書き出す。利用者の入力からツールの実行までに、どのプラグインとコールバックがどの順で走るか
3. 9 カテゴリを点検する
4. 攻撃のシナリオを流す。テストが無ければ台本のモデルで書く

規則
- シナリオは、防御を外すと攻撃が通り、戻すと止まることを確かめたものだけを「確認済み」にする。防御を外しても止まるなら、テストが何も確かめていない
- 判断に State の値（役割、利用者の ID、回数、自律のレベル）を使っていれば、そのカテゴリは要改善以下
- 形の照合（正規表現）だけの防御は、効いていても要改善。最小権限や承認と組み合わせているかを見る
- 本番投入には、S-1〜S-8 の全件適合に加えて、失敗したシナリオが 0 件であることを求める

出力には、項目ごとの結果の表の後に次の 2 つを足す

```markdown
## セキュリティのカテゴリ
| カテゴリ | 判定 | 根拠 | 次の一手 |
| --- | --- | --- | --- |

## シナリオ
| シナリオ | 防御なし | 防御あり | テスト |
| --- | --- | --- | --- |
| ツールの結果に仕込んだ指示 | 通る | 止まる | `test_indirect_injection.py::...` |
```

## 本番投入の判定

- S-1〜S-8 は全て適合が必須。1 件でも欠ければ投入しない
- ほかの観点（A / O / C / Q の合計）は、未対応が 0 件、かつ要改善が 3 件以内なら、改善計画を付けて投入を判断できる。対象外は数えない
- それを超えるなら、改善計画を作ってから再レビューする

## 出力の形

```markdown
## 対象
- エージェント: ...
- 範囲: 設計全体 / PR #... の変更

## 判定
本番投入: 可 / 条件付きで可 / 不可
- セキュリティ: 8 件中 N 件適合
- 要改善 N 件、未対応 N 件

## 項目ごとの結果
| ID | 判定 | 根拠 | 次の一手 |
| --- | --- | --- | --- |
| S-6 | 要改善 | `agent.py:42` の before_tool_callback で確認しているが、監査より後に並んでいる | 権限の確認をプラグインへ移す |

## アンチパターン
- 項目表に書いたことは繰り返さない。複数の項目にまたがる兆候だけを書く

## 改善計画（要改善と未対応がある場合）
- 優先の順に、どの項目を、誰が、いつまでに。担当者と期限が分からなければ「未定」と書く
```

PR のレビューでは、該当しない観点の表は省き、「対象外」と 1 行書く。

## 変更と項目の対応

| 変更の種類 | 見る項目 |
| --- | --- |
| エージェントやサブエージェントの追加、分割 | A-1〜A-5、C-1、Q-2 |
| Instruction の変更 | A-6、S-3、Q-2、Q-5 |
| ツールの追加、変更 | A-2、S-1、S-2、S-6、O-2、O-3、Q-3 |
| A2A / MCP の接続先の追加 | A-4、S-1、S-4、S-6、O-3 |
| モデル、キャッシュ、Compaction の設定 | C-1〜C-5 |
| ログ、トレース、メトリクスの変更 | O-1、S-5 |
| セッション、メモリの設定 | O-5、S-5 |
| デプロイの設定 | S-4、S-7、O-1、C-4 |
