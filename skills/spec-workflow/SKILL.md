# スペック駆動開発スキル

要求 / 設計 / タスクを対応付け、仕様と実装のずれを確認できる状態にする
既存の構成と依頼された実装範囲を保つ

## 手順

### 1 既存の仕様と依頼範囲を確認する

初回セットアップ / 機能追加 / バグ修正 / 仕様更新のどれかを決め、現在の文書と関連コードを読む
更新前には文書の現状を取得する
必要な永続ドキュメントが無い場合だけ、[永続ドキュメントのテンプレート](assets/persistent-docs-template.md)から作成案を出す

通常は`docs/`のプロダクト要求 / 機能設計 / アーキテクチャ / リポジトリ構造 / 開発規約 / 用語集を参照し、作業単位の文書は`.steering/YYYYMMDD-kebab-title/`へ置く
ここに`requirements.md` / `design.md` / `tasklist.md`を作る
SpecKit採用済みのリポジトリでは既存の`.specify/`と`specs/`を使い、対応する文書へ反映する
利用者が指示していない既存仕様の移動と、ツールの自動導入は禁止

### 2 要求を作り、未決事項を具体化する

[要求のテンプレート](assets/steering-requirements-template.md)を使い、受け入れ条件に識別子を付ける
機能追加ではユーザーストーリー / 制約 / 対象外を記す
バグ修正では再現条件 / 現在と期待する挙動 / 保つ挙動 / 回帰確認を記す

設計や受け入れ判定を変える未決事項があれば、必要な問いだけを確認する
回答と反映先を要求に残し、未回答の仕様を推測で実装へ埋めない
判断が不要な部分は先へ進める

### 3 設計をレビューしてからタスクにする

[設計のテンプレート](assets/steering-design-template.md)で方針 / 影響範囲 / モデル / インターフェース / 検証をまとめる
タスク作成前に、受け入れ条件がモデルや処理と検証へ結び付くか、既存の責務分担に合うかを確認する
データ永続化 / モデルの項目 / 起動確認を扱う場合やSpecKitの工程へ対応付ける場合は、[設計レビューの観点](references/spec-review.md)の該当部分を読む

[タスクのテンプレート](assets/steering-tasklist-template.md)で依存関係 / 対応する受け入れ条件 / 完了条件 / 検証方法を記す
要求から設計 / タスク / 検証までに漏れが無いことと、永続ドキュメントの更新要否を確認する

### 4 許可された範囲を実装し、挙動を確認する

実装まで求められている場合はタスクに沿って進め、同じ範囲への一般的な承認を工程ごとに追加しない
実装範囲を変える未決事項や、別途の権限が必要な操作だけを確認する
テスト / lint / 型チェックなど、変更に必要な検証を実行する
アプリの変更では起動と代表操作を確認し、永続化が対象なら再読み込み後の状態と要求した異常系も確認する
成功したコマンドだけで完了にせず、受け入れ条件ごとの結果 / 未確認事項 / 残作業をタスクへ反映する

## 出力形式

作成した文書だけでなく、判断と実装の現在地が分かる形で返す
未決事項が無ければ承認待ちの欄を作らず、許可された次の作業へ進む

```markdown
## 作成 / 更新

- ...

## 確認済み

- 要求と設計の対応 / 検証結果

## 未決事項

- 判断が必要な問い / 影響する範囲

## 実装範囲と次の作業

- 依頼された範囲 / 実施済み / 残作業
```

実装した場合は、変更ファイル / 検証結果 / 残リスクも報告する
