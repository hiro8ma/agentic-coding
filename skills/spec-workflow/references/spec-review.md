# 設計レビューの観点

要求と設計を照合してからタスクへ分ける
該当する観点だけを使い、現在の要求にない機能や基盤を増やさない

## 未決事項の確認

設計や受け入れ判定を変える曖昧さがある場合は、要求の作成後、計画の確定前に具体化する
回答が無くても進められる文書や作業は進め、判断が必要な部分を保留する
実装中に未決仕様が見つかった場合も、推測で補わず要求と設計へ戻す
実装の依頼を受けていること自体は、工程ごとに確認し直す理由にはならない

## 要求から検証までの対応

- 受け入れ条件が、モデルの項目 / 処理 / 状態遷移 / 外部インターフェースのどこで実現されるかを示す
- 各項目と分岐に要求や既存契約上の用途があるかを確認する
- 作成日時 / 更新日時 / 編集操作などの新規追加は、現在の要求や既存契約で必要な場合に限る
- タスクから受け入れ条件と検証へ戻れるようにし、対応の無いタスクと検証できない条件を点検する

## 永続化が対象の場合

保存形式の破損や型不一致 / 読み込み失敗 / 保存失敗を別々の条件として扱う
失敗時に表示する内容、メモリ上の状態、保存済みデータを残すかどうかを要求で決める
たとえば保存失敗を空のデータと同じように扱うと、画面では成功したように見えて再読み込みで変更が消える場合がある
黙って初期化するか、操作を保留するかなどの選択は、利用者の期待を確認してから設計へ反映する

成功時の保存と再読み込みだけでなく、要求した失敗条件を再現して期待する挙動を観測する
破損データや保存失敗を再現していない場合は未確認とし、正常系の成功で置き換えない
永続化を扱わない変更には、この観点を適用しない

## アプリの変更を確かめる場合

起動手順と代表操作を用意し、画面や出力が受け入れ条件を満たすかを確認する
永続化が対象なら再読み込み後にも状態が保たれるかを見る
テスト / lint / 型チェックの成功は、それぞれが観測した範囲の証拠として扱う
実行環境の制約で起動や操作ができなければ、理由と残りの確認対象を記す

## SpecKit採用済みの場合

既存の`.specify/`と`specs/`を保ち、要求は`spec.md`、設計は`plan.md`、タスクは`tasks.md`など、そのリポジトリの文書へ反映する
constitutionに定めた原則があれば使い、同じ原則の別文書を増やさない
Skillを使うだけでSpecKit CLIや依存ツールのインストールを要求しない

現行のCodex連携は`.agents/skills/`にSkillを置き、`$speckit-specify`などで呼び出す
教材や他のホストの`/speckit.*`という表記を、そのままCodexのコマンドと扱わない

| 工程 | SpecKitでの位置 |
|---|---|
| 要求を具体化する | `$speckit-specify`の後、必要なら`$speckit-clarify`を使ってから`$speckit-plan`へ進む |
| 設計をレビューする | 計画の後、`$speckit-tasks`の前に要求 / モデル / 処理 / 検証を確認する |
| 文書間の整合性を見る | タスク作成後、`$speckit-implement`の前に`$speckit-analyze`で照合する |
| 実装後に仕様と照合する | `$speckit-converge`で仕様と実装のずれを確認する |

Clarifyは公式では任意の工程で、未決事項が無ければ省ける
Tasks前の設計レビューと、Tasks後のAnalyzeは別の確認として扱う
使えるSkillやコマンドは導入済みの版で確認し、未導入の工程は対応する文書を読み取って確認する
