# rule-loops

エージェントの指示ファイル（CLAUDE.md / AGENTS.md / メモリのファイル）のルールを、利用者の指摘がどう取り込まれたかで並べる
Python 3.9以降の標準ライブラリだけで動く

## なぜ作ったか

指示ファイルのルールの多くは、利用者に指摘された後に足したものである
指摘のきっかけは `**Why:**` の行に日付つきで残すことが多い

組織学習の言葉では、指摘の取り込み方は次の3つに分かれる

| 取り込み方 | 中身 | 例 |
|---|---|---|
| シングルループ | 行動だけを変える | 「〜を付けない」を1行足す |
| ダブルループ | 同じ種類の失敗がまた起きた後に、判断の前提を書き換える | 「短い返事を許可と読まない」を、「出す直前に毎回許可を求める。条件付きの指示を許可と読まない」に書き換える |
| 仕組みでの強制 | hook / CI / lint / スクリプトが、モデルの外で止める | レビュー依頼のコマンドを hook で止める |

この道具は、次の問いに答える材料を並べる

- 書いた後に、また同じ指摘を受けたルールはどれか
- Why がなく、後から見直せないルールはどれか
- また指摘を受けたのに、文章だけで守らせているルールはどれか

答えは出さない
並べた候補を、人が読んで決める

## ルールと Why の取り方

ルールの単位は次の2つ

- 箇条書きの一番上の項目（番号付きを含む）
  - 下にネストした項目は、その項目の中身に含める
- 見出しの節
  - 直下に段落があるか、節に付く Why があるときだけ数える
  - 節の本文には、見出し、段落、節の中の箇条書きを含める
  - 見出しの前の段落は1つの節とみなし、frontmatter の `description`（なければ `name`）を見出しにする

数えないもの

- リンクで始まる箇条書き（`- [名前](file.md) — 説明`）
  - 索引か参照の一覧とみなす
- コードブロック、表、引用（`>`）、frontmatter

Why の行は、行頭（箇条書きの記号の後）が `**Why:**` / `**Why**:` / `Why:` / `**理由:**` / `なぜ:` のもの
大文字と小文字、全角のコロンを問わない
その行から、空行か次の太字の札（`**How to apply:**` など）までを Why の文とする

| Why の置き場所 | 付け先 |
|---|---|
| 箇条書きの下にネストした Why（何段下でも） | 一番上の項目のルール |
| 項目の続きの行の Why | その項目のルール |
| ネストしていない Why の箇条書き | 節のルール |
| 段落の Why | 節のルール |

ネストしていない Why の箇条書きは、直前の項目でなく節に付ける
節の終わりに置いた Why は、節の全体の理由であることが多いため

自分の Why がなく、節に Why がある箇条書きは「節」と出す
日付は節のルールにだけ数え、箇条書きには数えない

## 日付と再発

Why の文から、次の日付を拾う

| 形 | 例 | 拾う場所 |
|---|---|---|
| YYYY-MM-DD | `2025-03-04` | Why の文のどこでも |
| YYYY/M/D | `2025/7/8`、`2025/07/08` | Why の文のどこでも |
| M/D | `7/20` | Why の書き出しと文の頭（「。」の後、". " の後、行の頭）。英語の "On" が前にあってもよい |

- M/D の年は、同じ Why の前にある年付きの日付から取る
  - 前になければ後ろから取り、どちらもなければ年なし（`--07-20`）で出す
- 文中の M/D は拾わない
  - 「10/13に外れていた」のような事実の日付を、指摘を受けた日と数えないため
- ありえない日付（`2025-13-01`、`2/30`）と、日のない `2025-12` は拾わない
- Why の外の日付（本文や見出しの日付）は数えない

1つのルールの Why の日付を重複なしで数え、2つ以上なら「再発」とする

### 同じ節の複数のルールに日付が分かれている節

同じ種類の指摘をまた受けたとき、Why を足すのでなく、隣に別の箇条書きを足すことがある
ルールの単位では、これを再発と数えない

そこで、同じ節の2つ以上のルールが、合わせて2つ以上の日付を持つ節を別に並べる
同じ種類の失敗かどうかは見ないので、関係のない指摘が同じ節に並んだだけのものも出る
要約の再発の件数には含めない

## 仕組みの欄

ルールの本文（Why を除く）に次の語があれば、語と行を証拠として出す

| 種類 | 語 |
|---|---|
| hook | hook / hooks / pre-commit / PreToolUse / PostToolUse / UserPromptSubmit / SessionStart / SubagentStop / フック |
| CI | CI / GitHub Actions / `.github/workflows` |
| lint | lint / linter / `golangci-lint` などの `-lint` / ruff / eslint / staticcheck / clippy / prettier / go vet / リンター / リント |
| script | script / scripts / スクリプト / `.sh` `.py` `.ts` `.js` `.mjs` のパス |
| tool | `tools/` の下のパス / `settings.json` / execpolicy / `.rules` のファイル / `--tool` で足した名前 |

英字の語は、前後が英数字でないときだけ拾う（`webhooks` / `CIRCLE` は拾わない）
語に触れているかだけを見て、その仕組みがルールを実際に止めるかは見ない

## 札の欄

ルールの本文（Why を除く）の語で札を付ける
条件の語があれば、行動の語があっても「条件」にする

| 札 | 語 | 拾いたいもの |
|---|---|---|
| 条件 | 毎回 / 直前に / 〜だけを〜と読む（みなす / 扱う） / 〜と読まない（みなさない / 扱わない） / 許可 / 承認 / 基準 / every time / right before / approval / permission / consent / counts as / treat ... as | 判断の前提（何を許可とみなすか、いつ確かめるか）を書き換えたルール |
| 行動 | 禁止 / 必ず / 文末の「〜ない」 / 文末の動詞の終止形（う段の仮名。「いる」「ある」を除く） / never / do not / don't / must not / avoid / always / must | 具体的な操作の禁止と指示 |
| なし | どちらの語もない | |

札は語の一致で付けた目安で、シングルループとダブルループの分類として正しいことは示さない

- 「許可」は、許可の基準を書き換えたルールにも、許可を取る手順を書いただけのルールにも当たる
- 文末の動詞は、説明の文（「〜で動く」）にも当たる
- 英語は助動詞と否定の語しか見ない。命令形だけの文（"Use X"）は「なし」になる
- ルールが書き換えられたかは見ない。指示ファイルの履歴を読まないため

## 出力

`fixtures/rules.md` の出力の先頭は次のとおり
この後に「Why がないルール」「同じ節の複数のルールに日付が分かれている節」「すべてのルール」の表が続く

```text
# rule-loops

読んだファイル1件
ルール9件（箇条書き7件 / 見出しの節2件）
自分の Why があるルール5件 / 節の Why だけがあるルール3件 / Why がないルール1件
再発したルール（Why の日付が2つ以上）4件
再発していて、hook / CI / lint / スクリプト / 道具に触れていないルール2件
同じ節の複数のルールに日付が分かれている節1件

仕組みと札の欄は語の一致で付けた目安で、分類の正しさは示さない

```

`--json` では、`summary` に件数、`rules` にルールごとの次の項目、`section_overlaps` に節の一覧を出す

| 項目 | 中身 |
|---|---|
| `file` / `line` / `heading` / `heading_path` | 場所。`heading_path` は上の階層の見出しを含む |
| `kind` | `item`（箇条書き）か `section`（見出しの節） |
| `has_why` / `why_scope` | Why の有無。`why_scope` は `rule`（自分の Why）/ `section`（節の Why だけ）/ `none` |
| `why_lines` | Why の行の番号 |
| `incident_dates` | Why の日付。年なしは `--MM-DD` |
| `recurring` | 日付が2つ以上か |
| `structural` | 仕組みの語の証拠（`name` / `match` / `line` / `text`） |
| `fix_kind` / `fix_markers` | 札（`criterion` / `action` / `unlabeled`）と、当たった語の証拠 |

## 使う

```bash
python3 tools/rule-loops/rule_loops.py CLAUDE.md
python3 tools/rule-loops/rule_loops.py CLAUDE.md ~/.claude/projects/<project>/memory/
python3 tools/rule-loops/rule_loops.py --glob 'feedback_*.md' ~/.claude/projects/<project>/memory/
python3 tools/rule-loops/rule_loops.py --json AGENTS.md > rules.json
python3 tools/rule-loops/rule_loops.py --tool deploy-guard AGENTS.md
```

| 引数 | 動き |
|---|---|
| `PATH` | ファイルかディレクトリ。ディレクトリは下の階層まで読み、`.` で始まるディレクトリとファイルは読まない |
| `--json` | JSON で出す |
| `--glob PATTERN` | ディレクトリで読むファイル（既定は `*.md`） |
| `--tool NAME` | 仕組みとして数える道具の名前。何度でも付けられる |

終了コードは0
読めないパスを渡したときだけ2

メモリのディレクトリには、指摘のルール（`feedback_*.md`）のほかに、作業の状況や利用者の情報のファイルも入る
それらの箇条書きも「Why がないルール」に数えるので、ルールだけを見るときは `--glob` で絞る

## テスト

```bash
python3 -m unittest discover -s tools/rule-loops
```

fixture は合成の指示ファイルで、実在の組織や人の情報は含まない
テストでは次のものを確かめる

- 日付が2つある Why と、日付が1つ / 同じ日付が2つの Why
- Why のないルール
- hook に触れるルールと、Why の中だけで hook に触れるルール
- 日本語と英語の Why、`**Why**:` と `**理由:**` の形
- 3つの日付の形、年の補い方、拾わない日付
- ネストした箇条書き（2段下の Why、ネストした項目の仕組みの語）

Python 3.9.6と3.15.0で通ることを確かめた

次のように実装を壊すと、テストが落ちることも確かめた
壊した実装はテストの後に元に戻した

| 壊したところ | 落ちたテスト |
|---|---|
| ネストした Why の箇条書きを捨てる | Why の付け先 / 再発 / 要約の件数 / 再発したルール / 節の一覧 / Why の行の番号 / Why の外の日付 |
| ネストしていない Why の箇条書きを節に付けない | Why の付け先 / 要約の件数 / 再発したルール / 文章だけのルールの一覧 |
| YYYY/M/D を読まない | 日付の形 / 要約の件数 / 再発したルール / 文章だけのルールの一覧 |
| M/D を読まない | 日付の形 / 要約の件数 / 再発したルール / 文章だけのルールの一覧 |
| 再発のしきい値を3つ以上にする | 再発 / 要約の件数 / 再発したルール / 文章だけのルールの一覧 |
| 仕組みの語から hook を外す | 仕組みの語 / Why の後の太字の札 |
| 英字の語の境界を外す | 仕組みの語（`webhooks` / `CIRCLE`） |

## 限界

- 再発は、Why に書いた日付の数でしか見ない
  - 日付を書かない Why（「同日」「前回」）と、Why のないまま足した指摘は数えない
  - Why に事実の日付（「2025-03-01に移した」）を年付きで書くと、指摘を受けた日と区別できず再発に数える
  - 見出しに書いた日付（「## 追記（2025-09-02）」）は数えない
- 文中の M/D を拾わない規則は、手元のメモリのディレクトリで、事実の日付を指摘の日と数えた2件を見てから足した。調整に使っていないデータで精度を測っていない
- ネストした項目に別のルールを書いても、一番上の項目と合わせて1つのルールに数える
- 仕組みの欄は、語に触れているかだけを見る
  - 「CI が緑になってから出す」「lint を流す」のように、ルールの条件や手順として触れた文も仕組みに数える。手元の指示ファイルで試すと、仕組みに数えたルールの多くはこの形だった
  - 逆に、hook で止めているルールでも、指示ファイルにその hook を書いていなければ「なし」になる。`settings.json` や hook の設定は読まない
- 古いルールを消したか（アンラーニング）は見ない。今のファイルしか読まないため
- Markdown の文法を全部は読まない
  - setext の見出し（`===` / `---` の下線）、HTML のリスト、`* * *` の水平線は扱わない

## 確かめていないこと

- 札の正しさ。正解を付けたデータで、適合率と再現率を測っていない
- AGENTS.md と GEMINI.md の実物での動き。合成の fixture と、手元の CLAUDE.md とメモリのディレクトリだけで試した
