# term-check

用語集の表に沿って、文から使わない語を探す道具
同じ語でも、出し先（コミットメッセージ / PR のタイトルと本文 / 文書）ごとに、使ってよいかを分ける
ファイルを調べる `lint`、用語集を調べる `glossary`、Claude Code と Codex の PreToolUse(Bash) の `hook` の3つのコマンドがある
判定は語の文字列の一致で行い、LLM は使わない
Python 3.9以降の標準ライブラリだけで動く

## なぜ作ったか

チームの共通言語についての教材は、用語集に語の定義だけでなく、使う場面と、その語で期待する判断までを書くよう勧めている
定義だけの用語集では、語を知っていても、どの場面で何を決めればよいかが揃わない

| 列 | 中身 | 例 |
|---|---|---|
| 使う語 | 揃える先の語 | 発注 |
| 使わない語 | 揃える前の言い方 | オーダー |
| 使う場面 | その語を使う場面 | 架空商事に商品を頼む行為を書くとき |
| 期待する判断 | その語を読んだ人に取ってほしい判断 | 頼む行為は発注、頼まれた側の記録は受注と書き分ける |

もう1つのきっかけは、出し先で正しさが変わる語
利用者の規則では、顧客の社名の後ろに付ける敬称の「様」を、チャットとメモでは付け、コミットメッセージと PR のタイトル / 本文では付けない
規則を書いた後にも、エージェントがコミットメッセージに敬称を入れることが続いた
文書では正しい語をコミットでは止めたいので、用語集の行ごとに出し先（対象）を持たせた

hook にもしたのは、`tools/gh-confirm` と同じ理由
プロンプトの規則はモデルが読んで判断に使うもので、モデルが取り違えたときにコマンドを止める力はない
hook は、モデルの外の実行の層で、コマンドが走る前に毎回同じ規則で文を調べる

## 用語集の形

`fixtures/glossary.md` の表は次のとおり
社名と語はどれも架空のもの

| 使う語 | 使わない語 | 除く語 | 対象 | 使う場面 | 期待する判断 |
|---|---|---|---|---|---|
| | 様 | 仕様 / 模様 / 同様 / 多様 / 様子 / 様式 / 様々 / 一様 / 様相 / 異様 | commit / pr | コミットメッセージと PR のタイトル / 本文で、取引先の社名に触れるとき | 社名だけを書く（架空商事）、チャットとメモでは敬称を付けるので docs には広げない |
| 発注 | オーダー | オーダーメイド | all | 架空商事に商品を頼む行為を書くとき | 頼む行為は発注、頼まれた側の記録は受注と書き分ける |
| 見積書 | 見積もり書 / 御見積書 | | docs / pr | 架空商事に出す金額の書類を指すとき | 書類の名前は見積書に揃え、金額を見積もる作業は見積もりと書く |
| サーバー | サーバ | | all | 機械やプロセスを指すとき | 長音の付いたサーバーに揃える |
| main | master | | all | 既定のブランチを指すとき | 既定のブランチは main と書き、ほかのリポジトリの master を指すときはコードの書式で囲む |

| 列 | 書き方 |
|---|---|
| 使う語 | 揃える先の語（空なら、使わない語だけを決める行になる） |
| 使わない語 | 文から探す語（空なら、lint と hook はその行を使わない） |
| 除く語 | 使わない語を含むが、使ってよい語 |
| 対象 | `commit` / `pr` / `docs` / `all` のどれか（`all` はどの出し先にも当てはまる） |
| 使う場面 | 当たりの理由の文に出す |
| 期待する判断 | 当たりの理由の文に出す |

- 使う語 / 使わない語 / 除く語は、前後に空白のある ` / ` で区切って複数書ける
  - 空白の無い `/` は語の一部にする（`N/A` は1つの語）
  - 同じ語を2回書いても1回にする
- 対象は `/` で区切って複数書ける（前後の空白は無くてもよい）
- 見出しに「使う語」か「使わない語」のある表を、用語集の表として読む
  - 6つの列の名前で列を読み、列の順は問わない
  - ほかの表とフェンスの中の表は読まない
  - 用語集の表がいくつあっても、全部を読む
- 表の行は `|` で始める
  - セルの中の縦棒は `\|` と書く
  - 全部のセルが空の行は飛ばす

次の形は用語集の誤りにして、どのコマンドも読まない

| 誤り | 例 |
|---|---|
| 用語集の表が無い | 見出しに使う語も使わない語も無い / 見出しの次の行が `\|---\|` の区切りの行でない |
| 見出しに6つの列がそろわない | 期待する判断の列が無い |
| 行の列の数が見出しと違う | 6つの列の表に5つのセルの行がある |
| 対象が空か、決まった値でない | `commit / slack` |
| 使う語も使わない語も無い | 対象と場面だけの行 |

使う場面と期待する判断が空の行は、誤りにしない
`lint` と `hook` はその行も使い、`glossary` だけが欠けとして数える

## 当たりの決め方

- 出し先が対象に入る行の使わない語を、文の行ごとに文字列で探す
  - 大文字と小文字を区別する
  - 語の境界は見ない（`master` は `mastery` にも当たる）
- 当たった位置の使わない語が、その位置で除く語の一部なら、当たりにしない
  - 「架空商事様の仕様」は、社名の後ろの様だけが当たる
  - 語が前にある除く語（様子 / 様式 / 様々 / 様相）も、語が後ろにある除く語（仕様 / 模様 / 同様 / 多様 / 一様 / 異様）も見る
  - 「仕様様」は2つ目の様が当たる（仕様の一部は1つ目の様だけ）
  - 除く語の中に使わない語が2回ある語（使わない語「ちゃん」と除く語「ちゃんちゃんこ」）は、どちらの位置も除く
- 使う語も除く語と同じに扱う
  - 使う語「サーバー」と使わない語「サーバ」の行で、サーバーは当たらない
- 1つの行の使わない語どうしが同じ位置で重なれば、長い語だけを当たりにする
  - 使わない語「オーダー / オーダー書」で、「オーダー書」は1つの当たりにする
- 同じ語を禁じる行が2つあれば、行ごとに当たりを出す
- 次の中は見ない
  - フェンスのコードブロック（バッククォートとチルダ、閉じないフェンスは文の最後まで）
  - インラインコード
  - `http://` / `https://` の URL（リンクの文は見て、リンクの先は見ない）
- 伏せた部分は同じ長さの空白に置き換えるので、字の位置は元の文の位置のまま

## lint

```bash
python3 tools/term-check/term_check.py lint --glossary glossary.md --target docs notes/ README.md
python3 tools/term-check/term_check.py lint --glossary glossary.md --target commit --json msg.txt
git log -1 --format=%B | python3 tools/term-check/term_check.py lint --glossary glossary.md --target commit -
```

| 引数 | 動き |
|---|---|
| `--glossary` | 用語集の Markdown のファイル（必須） |
| `--target` | 文の出し先（`commit` / `pr` / `docs` のどれか、必須） |
| `PATH` | 読むファイルかディレクトリ（いくつでも渡せる、`-` で標準入力を読む） |
| `--json` | JSON で出す |
| `--report-only` | 当たりがあっても終了コード0を返す（入力の誤りは2のまま） |

- ディレクトリは、下の階層の `*.md` を名前の順に読む
  - `.` で始まるディレクトリは読まない
- ファイルを直に渡したときは、拡張子を問わず読む（コミットメッセージの `.txt` など）
- 同じファイルを2回渡しても、1回だけ読む
- UTF-8 で読み、先頭の BOM は外す

`fixtures/texts/commit_message.txt` に流した出力は次のとおり

```text
$ python3 tools/term-check/term_check.py lint --glossary tools/term-check/fixtures/glossary.md --target commit tools/term-check/fixtures/texts/commit_message.txt
# term-check

出し先 commit / 読んだファイル1件 / 当たり4件

## tools/term-check/fixtures/texts/commit_message.txt

- 1行目11字目「様」→ 使う語なし（用語集の8行目）
  - 行「feat: 架空商事様のオーダーの画面を直す」
  - 使う場面 コミットメッセージと PR のタイトル / 本文で、取引先の社名に触れるとき
  - 期待する判断 社名だけを書く（架空商事）、チャットとメモでは敬称を付けるので docs には広げない
- 1行目13字目「オーダー」→ 使う語「発注」（用語集の9行目）
  - 行「feat: 架空商事様のオーダーの画面を直す」
  - 使う場面 架空商事に商品を頼む行為を書くとき
  - 期待する判断 頼む行為は発注、頼まれた側の記録は受注と書き分ける
- 4行目1字目「サーバ」→ 使う語「サーバー」（用語集の11行目）
  - 行「サーバの設定は master に入れてから直す」
  - 使う場面 機械やプロセスを指すとき
  - 期待する判断 長音の付いたサーバーに揃える
- 4行目9字目「master」→ 使う語「main」（用語集の12行目）
  - 行「サーバの設定は master に入れてから直す」
  - 使う場面 既定のブランチを指すとき
  - 期待する判断 既定のブランチは main と書き、ほかのリポジトリの master を指すときはコードの書式で囲む
```

- 同じファイルの2行目の「仕様」「同様」、3行目のインラインコードと URL の中の `master` は当たらない
- 同じ用語集で `--target docs` にすると、敬称の行が当てはまらないので、当たりは3件になる
- 当たりの無いファイルは出さない（JSON には出す）
- 字の位置は1から数える（全角の字も1字）
- 行は当たりの前後20字で切り、切ったところに「…」を付ける

`--json` を付けると、次の形で出す

| キー | 中身 |
|---|---|
| `summary` | `glossary`（用語集のパス）/ `target`（出し先）/ `files`（読んだファイルの数）/ `hits`（当たりの数） |
| `files[].path` | ファイルの名前（標準入力は `-`） |
| `files[].hits[]` | 当たりごとの `line` / `column` / `word`（当たった使わない語）/ `excerpt`（前後20字の行）/ `rule`（用語集の行の `line` / `use` / `avoid` / `except` / `targets` / `scene` / `judgment`） |

## glossary

用語集の各行に、使う場面と期待する判断が書いてあるかを確かめる

```text
$ python3 tools/term-check/term_check.py glossary --glossary tools/term-check/fixtures/incomplete_glossary.md
# term-check glossary

規則4件 / 使う場面と期待する判断がそろう1件 / 欠け3件

## 欠けた規則

- 6行目 使う語「受注」
  - 欠け 使う場面
- 7行目 使う語「納品書」 / 使わない語「納品伝票」
  - 欠け 期待する判断
- 8行目 使う語「検収」 / 使わない語「受け入れ確認」
  - 欠け 使う場面 / 期待する判断
```

## 終了コード

| コマンド | 0 | 1 | 2 |
|---|---|---|---|
| `lint` | 当たりが無い / `--report-only` を付けた | 当たりがある | パスが無い / ファイルを UTF-8 で読めない / 用語集を読めないか誤りがある / 引数の誤り（`--report-only` を付けても2） |
| `glossary` | 全部の行に使う場面と期待する判断がある | 欠けた行がある | 用語集を読めないか誤りがある / 引数の誤り |
| `hook` | いつも0 | | |

`lint` は、入力の誤りがあると、ほかのファイルも出力せずに2を返す

## hook

PreToolUse(Bash) の hook として、コマンドが走る前に、コミットメッセージと PR のタイトル / 本文を調べる
当たりがあれば `permissionDecision` に `"deny"` を返し、当たりを並べた理由の文を返す
それ以外は何も出さずに通す

| コマンド | 読む文 | 出し先 |
|---|---|---|
| `git commit` | `-m` / `--message` の値（複数なら空行でつなぐ）と、`-F` / `--file` のファイルか標準入力 | `commit` |
| `gh pr create` / `gh pr new` / `gh pr edit` | `--title` / `-t` と、`--body` / `-b` の値と、`--body-file` / `-F` のファイルか標準入力 | `pr` |

次の書き方も読む

- `-m"..."` / `--message=...` / `-am "..."` のような、値を続けた形とまとめた短いフラグ
- `-m "$(cat <<'EOF' ... EOF)"` の `$( )` の中の、`cat` のヒアドキュメント / ヒアストリングと `echo` の出力
  - ほかのコマンドの `$( )` は空白に置き換えて、前後の文を読む
- `-F -` / `--body-file -` に、ヒアドキュメントかヒアストリングで渡した文
- `&&` / `||` / `;` / `|` / 改行でつないだコマンド、サブシェルの `( )` と `$( )` の中
- `bash -c` / `sh -c` / `eval` の文字列、`env` と変数の代入を前に付けたもの
- `git -C <dir>` / `git -c <key>=<value>` を前に付けたもの、`gh pr -R <repo>` のように前にフラグを置いたもの
- `-F` / `--body-file` の相対パスは、hook の入力の `cwd`（無ければ hook の作業ディレクトリ）から読み、前の `cd` と `git -C` の先を足す
  - UTF-8 で読み、先頭の BOM は外す

`git commit` の `-t` は `--template` で、`gh pr` の `-t`（`--title`）とは別に読む

次のものは通す

| 例 | 通す理由 |
|---|---|
| `echo "git commit -m ..."` | `git` が `echo` の引数 |
| `cat > note.md <<'EOF' ... EOF && git commit -m docs` | ヒアドキュメントは `note.md` に書く文で、コミットの文ではない |
| `git commit` / `git commit --amend --no-edit` / `git commit -C HEAD` | 文がコマンドの中に無い（エディタか前のコミットから取る） |
| `git commit --author "..."` | 作者の欄はメッセージではない |
| `git merge -m` / `gh pr comment --body` / `gh issue create` | 見るコマンドでない |
| 無いファイルか UTF-8 で読めないファイルの `-F` | 読めない |
| JSON が読めない / Bash 以外のツール / `command` が無い | 見るコマンドが無い |
| 用語集が無いか誤りがある | 標準エラーに理由を書いて通す |
| hook の引数の誤り（`--glossary` が無いなど） | argparse の誤りを0にする |
| 解析の失敗 | 通す |

Claude Code の PreToolUse の hook は、終了コード2で Bash の呼び出しを止める
hook や用語集の不具合で全部の Bash を止めないよう、この道具の hook は、当たりのとき以外は何もしない
見るコマンドの無い呼び出しでは、用語集を読まない

理由の文は次のとおり

```text
用語集で使わない語を含む
- コミットメッセージの1行目「様」→ 使う語なし（用語集の8行目）
  - 行「feat: 架空商事様の仕様を直す」
  - 使う場面 コミットメッセージと PR のタイトル / 本文で、取引先の社名に触れるとき
  - 期待する判断 社名だけを書く（架空商事）、チャットとメモでは敬称を付けるので docs には広げない
用語集の期待する判断に沿って書き直してから、もう一度実行する
```

コマンドの読み方は `tools/gh-confirm` の解析を写したもので、`$( )` の出力を語に入れるところだけが違う
1つのファイルを置くだけで動くよう、gh-confirm を import しない
gh-confirm の解析を直したら、こちらにも写す

### Claude Code に入れる

この変更では、どの設定にも入れていない
入れるなら、スクリプトと用語集をユーザーの設定の場所に置き、`~/.claude/settings.json` の `PreToolUse` に足す
すでに `PreToolUse` があれば、その配列に足す

```bash
mkdir -p ~/.claude/hooks
cp tools/term-check/term_check.py ~/.claude/hooks/
cp tools/term-check/fixtures/glossary.md ~/.claude/term-glossary.md
```

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$HOME/.claude/hooks/term_check.py\" hook --glossary \"$HOME/.claude/term-glossary.md\""
          }
        ]
      }
    ]
  }
}
```

- 写した用語集は、自分の語に書き換えて使う
  - 実在の社名を書いた用語集は、公開のリポジトリに置かない
- Claude Code の `deny` は呼び出しを止め、理由の文をモデルに返す
  - モデルは理由の文を読んで文を直し、コマンドを出し直す

### Codex に入れる

`--codex` を付けると、`deny` に加えて、同じ理由の文を `systemMessage` で利用者にも見せる（gh-confirm の `--codex` と同じ形）

```bash
mkdir -p ~/.codex/hooks
cp tools/term-check/term_check.py ~/.codex/hooks/
cp tools/term-check/fixtures/glossary.md ~/.codex/term-glossary.md
```

`~/.codex/hooks.json` に次を書く

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "^Bash$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$HOME/.codex/hooks/term_check.py\" hook --glossary \"$HOME/.codex/term-glossary.md\" --codex",
            "statusMessage": "用語集に沿っているかを確かめている"
          }
        ]
      }
    ]
  }
}
```

Codex は、管理者が配っていない hook を、利用者が `/hooks` で中身を確かめて信頼するまで動かさない
書いたら Codex を起動し、`/hooks` でこの hook を信頼する

### 試す

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"git commit -m \"feat: 架空商事様の仕様を直す\""}}' \
  | python3 tools/term-check/term_check.py hook --glossary tools/term-check/fixtures/glossary.md
```

## テスト

```bash
python3 -m unittest discover -s tools/term-check
```

fixture とテストの文面は架空のもので、実在の組織や人の情報は含まない
34件のテスト（139件のサブテスト）が Python 3.9.6と3.15.0で通り、ruff check と ruff format --check で確かめた

次のように実装を壊すと、テストが落ちることも確かめた
壊した実装は、リポジトリの外の複製で試し、壊す前の複製でテストが通ることを先に確かめた
83通りのどれも、置き換えが実装の中でちょうど1か所に当たることを確かめてから試した

- 最初の実行では、83通りのどれも生き残らなかったが、8通りは検査の失敗（FAIL）ではなく、テストの中の例外（ERROR）だけで落ちた
  - 用語集の誤りの型を見ないもの、Codex の `systemMessage`、hook の引数の誤り、hook の解析の失敗などで、例外が検査の前に出ていた
  - 例外の型と、hook が終わらずに0を返すことを検査するようにテストを直した
- 直した後は、Python 3.9.6と3.15.0のどちらでも、83通りの全部が検査の失敗（FAIL）で落ちた

| 壊したところ | 落ちたテスト（2件まで） |
|---|---|
| 除く語を見ない | 除く語の中の1つ目の語は当たらない / 除く語の中の2つ目の語も当たらない ほか18件 |
| 使う語の中の使わない語も当たりにする | 使う語の中の使わない語は当たらない / test_json_shape ほか1件 |

## 限界

- 文字列の一致だけで判定し、意味は見ない
  - 大文字と小文字を区別し、語の境界を見ない
  - 除く語は、位置が重なれば意味を問わず除く（「架空商事様式」のように、社名の後ろの様が除く語と重なると見逃す）
  - 表記の揺れ（全角と半角、ひらがなとカタカナ、送り仮名）は、使わない語に並べないと当たらない
- URL は ASCII の字だけを URL として伏せる
  - 和文の字を含む URL は、和文の字から後ろを文として読む
- 字下げのコードブロックと、HTML のコメントとタグは伏せない
- hook はコマンドの文字列しか読まない
  - 同じコマンドの中で先に書くファイル（`cat > msg.txt <<'EOF' ... EOF && git commit -F msg.txt`）は、hook の時点ではまだ無いか古い中身なので、無ければ通し、あれば古い中身を調べる
  - パイプで渡す標準入力（`printf ... | git commit -F -`）、`$(cat msg.txt)` で読むファイル、変数に入れたメッセージは読まない
  - エディタで書くコミットメッセージ（`git commit` だけ）は読まない
  - git の長いオプションの略（`--mess`）、`git commit --trailer`、`git merge -m` / `git tag -m`、`gh api` で作る PR、`gh pr comment` / `gh pr review` の本文は読まない
  - `-m=x` を、git は `=x` を値にするが、この道具は `x` を値にする
  - `cd` は、サブシェルの中のものも後ろのコマンドに効かせる
- モデルの取り違えを止めるためのもので、悪意のある入力を防ぐ境界ではない
  - 変数で組み立てたコマンドや、符号化した文字列を復号して渡す文は止めない

## 確かめていないこと

- Claude Code と Codex の実際のセッションで、この hook が `deny` を返し、モデルが理由の文を読んで直すこと
  - 出力の形は gh-confirm に合わせ、テストでは標準入出力だけを確かめた
- Codex の hook の入力に `cwd` が入ること（無ければ hook の作業ディレクトリから相対パスを読む）
- Codex の PreToolUse の `deny` が、理由の文をモデルに返すこと
