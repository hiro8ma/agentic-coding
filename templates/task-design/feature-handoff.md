# 既存実装の調査から機能の実装へ引き継ぐ

〈〉を今回の機能に置き換えて使う
保存を伴わない機能など、該当しない欄は理由を添えて省く
調査でコードから分かることを集め、実装依頼には探索の入口とコードにない判断を残す

## 調査依頼

〈利用者が何をできるようにしたいか〉を実装するため、既存実装を調査する
この依頼ではファイルを変更しない

- 機能の状態やモードを定義する場所と、その切り替え元を調べる
- 入力を受ける場所から、処理と表示が変わるまでの経路を調べる
- 設定値の取得元と反映箇所、保存と復元の経路を調べる
- 関連するテストと、既存手順にある検証コマンドを調べる

結果には、実在するリポジトリ相対パスと、そこで確認したことを対応させて残す
未確認事項は、何が不明かと次に確認する場所を分けて書く
コードから分からない仕様や操作を推測で埋めず、設計書の全文は作らない

## 実装依頼

### Goal

- 〈誰が / どの操作をすると / 何ができるようになるか〉

### Context Pointers

- 探索の入口は〈調査で確認した相対パスと役割〉
- 入力 / 表示 / 保存と復元 / テストの参照先は〈確認した相対パス〉
- コードにない判断は〈仕様として決めたことと根拠 / 残っている問い〉

### Constraints

- 維持する既存動作は〈対象と条件〉、スコープ外は〈今回変えない範囲〉
- 既存の保存形式について〈読み込み互換性と、必要なら移行方法〉を守る
- 外部依存 / feature flag / フォールバックは、今回必要な理由と既存の仕組みを確認して採否を決める
- 調査で残った問いが実装を左右する場合や、複数案の比較が必要な場合は、Planで方針を確認してから実装する

### Done When

- 〈入力と操作〉に対し、〈表示や処理の結果〉になることを確認する
- 〈保存する状態〉を保存し、再読込後に〈復元する状態〉になることを確認する
- 〈維持する既存動作と旧データの読み込み〉を確認する
- 〈調査で特定した対象テストと検証コマンド〉を実行し、結果を残す
- 未実行 / 未確認は理由と確認方法を残し、満たしていない受入条件を完了扱いにしない

完了報告には変更した挙動、検証の証拠、残った問いを簡潔に書く
