# モバイルアプリの1機能を作り直す受入条件

対象機能ごとに複製して使う
人が要件と受入条件を決め、AIが実装と検証を進め、人が証拠を見て受け入れる
必須条件の未記入 / 未確認は未完了として扱い、対象外は理由を残す

## Goal

- 対象機能は〈誰が / どの画面で / 何をする機能か〉
- 作り直す理由は〈現在の問題と、作り直した後に得たい状態〉
- 変換元と変換先は〈例としてObjective-CからSwift、または同じ機能をKotlinで実装〉
- 今回は振る舞いを保って別の技術へ移すtransformとする
  - 仕様を変える要求は〈別タスクへの参照〉に分ける
  - OSごとに同じ挙動にできない箇所は、受入条件で許容差を決める

## Context Pointers

- 旧実装と比較する基準は〈相対パス / コミット / 旧アプリの配布物〉
- 利用者の操作と期待する結果は〈仕様 / 画面遷移 / 既知の不具合〉
- 保存形式と通信仕様は〈相対パス / 匿名化した旧データ / API仕様〉
- 移植を伴う場合の比較基準は〈実行できる旧処理 / 人が確認した入出力 / 参考実装とその未検証範囲〉
- 開発環境の手順は〈既存のセットアップ / build / run / testの手順〉
- 人が判断する担当は〈要件と受入 / 実機利用の調整 / リリース〉

参照先が存在することを確かめ、足りないものは推定せず未確認欄に残す
project / scheme / variant / 実行先 / 対象テストは実プロジェクトから特定して記録する

## Constraints

- 変更範囲は〈対象画面と依存部分〉とし、周辺機能の整理は別タスクに分ける
- 既存の保存データと通信形式について、維持する互換性と必要な移行を〈具体的に記入〉する
- worktreeごとに依存関係を既存手順で準備する
  - iOSのDerivedDataなどの生成物は当該worktree内に置く
  - 実機のインストール先 / アプリデータ / 接続状態はworktreeで分離されないため、共有実機を同時に使う作業と利用時間を調整する
- CLIで再現するコマンドは実プロジェクトで確かめたものを記録する
  - 未特定の設定値から実行用スクリプトを作らない
  - シークレット / 端末の識別子 / 絶対ローカルパスを共有する文書やログへ載せない
- 旧版が動かない場合は比較できた範囲を明記し、挙動が同じだと断定しない
- 可逆性と判断が分かれる点は〈戻す手順 / 残る影響 / 設計の選択肢〉
- 人間が設計に関わる範囲と担当は〈外せない論点 / 採否を決める人 / AIへ任せる範囲〉
- 採用した設計について〈採用理由 / 受け入れるリスク / 後から変更できる根拠〉を残す
- 別OSへ移す場合は〈共通ロジックの一致条件 / OS固有UIの許容差と理由〉を区別する

判断材料が未確認であることを、人間の関与を減らす理由にしない
コードレビューの要否は既存のレビュー規則に従う

## Done When

実装前に、人が次の期待結果と許容差を確認する
各行に「操作と入力 / 観測する結果 / 比較方法」を書き、同じ条件で旧版と新版を比べる

| 受入条件 | 操作と入力 | 期待する結果と許容差 | 証拠 |
| --- | --- | --- | --- |
| 主な操作ができる | 〈代表的な操作〉 | 〈画面 / 出力 / 副作用〉 | 〈旧版と新版の記録〉 |
| 旧データを読める | 〈旧版で保存した匿名化データ〉 | 〈内容を保って表示 / 更新できる条件〉 | 〈読み込み結果〉 |
| 異常時も仕様どおり動く | 〈この機能に関係する通信失敗 / 権限拒否など〉 | 〈表示 / 再試行 / データを守る挙動〉 | 〈結果の記録〉 |

検証は次の順に進め、失敗した段階を直してから次へ進む

1. 既存の形式検査 / 静的解析 / ビルドと、対象機能のテストを実行する
2. 受入条件ごとに旧版と新版を比較し、旧データの読み込みを確かめる
   重要な条件を一時的に壊し、対応する検査が失敗することを確認してから元に戻す
3. シミュレータ / エミュレータで操作し、実機が必要な挙動を〈理由と対象端末の条件〉に絞って確認する
4. 人が画面 / 操作 / 許容差を確認し、受入結果を残す

実行の証拠には対象コミット、環境の版、コマンド、終了結果、ログや画像の相対パスを残す
コマンドの成功だけで受入条件を満たした扱いにしない

対象機能の受入と、配布するアプリ全体のリリース検証は分ける
リリース検証の範囲は〈既存のリリース手順への参照 / 今回必要な確認〉に従う
人が署名設定の妥当性とストア申請の可否を判断し、AIによるビルド成功を配布許可として扱わない

| 判定 | 結果と根拠 | 判断者 |
| --- | --- | --- |
| 対象機能の受入 | 〈合格 / 未完了 / 不合格と証拠〉 | 〈担当者〉 |
| リリース検証 | 〈結果 / 今回の対象外と理由〉 | 〈担当者〉 |
| 署名と申請 | 〈実施可否 / 今回の対象外と理由〉 | 〈担当者〉 |

未確認事項は〈何が不明か / なぜ確認できないか / 次に何を誰が確認するか〉を記入する
受入条件を満たせない場合は人に差分と影響を示し、条件の見直しか修正を決めて記録する
