# プラットフォーム間で機能を移植する判定条件

〈〉を対象機能に置き換え、振る舞いを保つ移植と仕様変更を分ける
移植元の調査は範囲を絞ってサブエージェントへ渡し、仕様と根拠を返させる

## 仕様の抽出

- 対象の機能と利用者の操作は〈入力から観測結果まで〉
- 入出力の意味と範囲は〈型 / 値の範囲 / 単位 / 失敗時の結果〉
- 保持する条件は〈閾値 / 境界の含み方 / 計算順序 / 保存形式〉
- 元コードで未定義の入力は〈移植先でも発生しない条件、または別途決める扱い〉

例として、SwiftのUInt8で受け取るRGB値は各成分が0から255に限られる
KotlinのIntで受け取る場合は、この入力条件を呼び出し元で保証するか、境界で検証するかを決める
範囲外の値を黙って丸める処理は元の仕様からは導けない

## 参照実装

調査側が作った参考コードは、言語と検証状態を添え、移植先の責務へ組み込む
参考コードだけを正解の基準にはしない

- 旧実装の参照先は〈実在する相対パス / 比較するコミット〉
- 移植先の入口は〈実在する相対パス / 入力条件を保証する場所〉
- 比較するロジックとUIの境界は〈独立して比較できる処理 / 実機で確認する操作〉

RGB判定の例は `r > 180 && g < 120 && b < 120 && (max(r, g, b) - min(r, g, b)) > 80` とする
共通fixtureの期待値は旧式と境界から固定し、移植先の出力から生成しない

| r | g | b | 期待値 | 判定の理由 |
| --- | --- | --- | --- | --- |
| 199 | 119 | 119 | false | 最大値と最小値の差が80 |
| 200 | 119 | 119 | true | 差が81で他の条件も満たす |
| 180 | 0 | 0 | false | rが180 |
| 181 | 0 | 0 | true | rが180を超える |
| 200 | 120 | 0 | false | gが120 |
| 200 | 0 | 120 | false | bが120 |

## 旧実装と移植先の比較

- 実在するコンパイラと既存の検証手順を調べ、実行コマンドとバージョンを記録する
- 両実装に同じfixtureを入力し、期待値と旧新の出力が一致することを確認する
- 差が出たら〈型 / 値の範囲 / 演算 / 入出力変換〉を切り分け、仕様変更として扱う差を人が判断する
- 実行できない環境や不足する依存は〈未実行の対象 / 理由 / 次の確認方法〉として残す

## UIの許容差と受入

- 比較条件は〈入力操作 / 端末条件 / データ〉、許容する差は〈配置 / 表示 / 操作感の具体的な差と理由〉
- ロジックの結果が一致することと、画面上で目的の操作ができることを分けて確認する
- 証拠は〈対象コミット / 検証結果 / ログや画像の相対パス〉に残し、人が許容差と受入を判断する
- 必須条件の未記入 / 未確認を完了扱いにせず、比較できた範囲だけを結果として報告する
