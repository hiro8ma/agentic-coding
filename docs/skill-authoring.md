# スキルを自作する

他社が配るスキルを受け取る側の話は [third-party-skills.md](third-party-skills.md) に、
Agent Skills の仕組みそのものは [agent-skills.md](agent-skills.md) にある。
この文書は作る側に絞る。

## 自作する動機

配布されているスキルは便利だが、自分の業務にそのまま合うものは無いことが多い。
提供元・導入実績・監査結果のいずれかで不審な点があれば、入れずに自作するのが最も安全になる。

スキルは Markdown とディレクトリだけで書けるため、初期コストは低い。
「この作業、スキルにできないか」と業務側から発想するのが入口になる。

## skill-creator

Anthropic が公式に提供するスキル作成支援スキル。
新規作成、テスト実行、性能測定、改善までを扱う。

Anthropic の基本スキルを入れていれば既に使える状態にある。
「スキルを作りたい」と話しかければ発動し、`/skill-creator` で明示的に呼ぶこともできる。

### 6 ステップのサイクル

```
1. 意図の整理   何を実現し、いつ発動すべきかを決める
2. ドラフト     SKILL.md の初版を作る
3. テスト       同じタスクをスキルあり / なしで実行する
4. 評価         出力を定性・定量の両面で見る
5. 改善         結果を踏まえて SKILL.md を直す
6. 完成         description を最適化してパッケージ化する
```

2 から 5 を繰り返す。ここが本体になる。

### 生成される成果物

```
manufacturing-weekly-report/
├── SKILL.md      トリガー定義 + 手順 + 置換手順
└── assets/
    └── template.html

manufacturing-weekly-report.skill   実体は ZIP
```

ディレクトリのほうを `~/.claude/skills/` に置いて再起動すれば Claude Code で使える。
`.skill` ファイルは claude.ai のアップロード画面へ渡すと Claude.ai や Claude Desktop でも使える。

内部では `init_skill.py` でスケルトンを作り、`package_skill.py` で ZIP に固める。

## SKILL.md を手書きできても skill-creator を使う理由

本体の価値は SKILL.md の生成ではなく、その後の工程にある。

### 1 テストと評価の自動化

同じタスクをスキルあり / なしで実行し、出力を並べて比較する仕組みが組み込まれている。
比較と採点を行う専用エージェント（grader、comparator、analyzer）が品質を判定し、
結果を HTML ビューアで確認できる。

スキルは書けても、**そのスキルが本当に出力を改善しているかを測る仕組み**を自作するのは重い。
ここを持っているかどうかが、感覚と数字の分かれ目になる。

### 2 description の自動最適化

`description` はスキルの発動を制御するフィールドで、トリガー精度に直結する。
Claude はユーザーの入力とこの文字列を照合して、読み込むかを判断する。

だから「週報」だけでなく「週次報告」「生産報告」「生産週報」「今週の報告」「生産実績まとめ」と、
ユーザーが使いそうな表現のバリエーションを網羅する必要がある。

skill-creator は eval セットを train / test に分け、Claude に改善案を出させ、
テストスコアで最適版を選ぶ。SKILL.md 本体を手書きしても、description だけこの仕組みに乗せられる。

### 3 `scripts/` に切り出すべき箇所の発見

テストと改善のループを回していると、**Claude が毎回同じようなコードを書く処理**が見つかる。
それが `scripts/` に切り出す候補になる。

最初から完璧なスクリプトを用意するより、繰り返し実装されている処理を見つけて切り出すほうが、
無駄が出ない。スキルの 3 要素（指示・スクリプト・リソース）のうち、
スクリプトは最初から要るものではなく、観測してから足すものになる。

## 配布されているスキルから学べる設計

受け取り側で調べた 4 つ（Notion / Firecrawl / Playwright / Remotion）から、
自作に持ち込めるものを挙げる。詳細は [third-party-skills.md](third-party-skills.md)。

- 手段が複数あるなら、安い順に試す段階を書く
- 大きな出力はファイルに逃がし、パスだけ渡す
- 並列化を促すなら stdin の扱いまで書く
- スキルを分割し、入口から必要な分だけ降りられるようにする
- 評価データを同梱し、効いているかを受け手が検証できるようにする
- 導入手順に「読み込まれたことの確認方法」を書く

最後の 1 つは実際に踏んだ。インストール成功と読み込み成功は別物で、
ディレクトリ階層が 1 段ずれるだけで無言で消える。

## 出力を目で確認する手順を持つ

型チェックが通っても生成物が壊れていることがある。
動画・画像・長文など、視覚物を出すスキルでは特に起きる。

作る側なら、SKILL.md に確認手順まで書いておく。
使う側なら、自分の手順として持っておく。どちらも無いと、壊れたまま完成扱いになる。
