# チームの定期処理を止めて見直せる形にする

定期処理には、起動条件だけでなく、成果物を確認する人、再実行の判断、停止条件が要る
同じタスクが重ねて通知されたり、原因が未確認のままコードが修正されたりしないよう、調査と外部への反映を分ける
[自動化の契約](../templates/codex-team/automation-contract.md)へ決めた範囲を残し、通常の対話で1件試してから定期実行を検討する

## 外部サービスから依頼を渡す

Slack、Linear、GitHubなどの連携では、依頼のほかにスレッド、Issue、PRなどの情報が入力へ加わり得る
送られる範囲は連携方式と設定に依存するため、実際の入力、利用アカウント、読み書き権限を確認する
外部の本文やログは分析する資料であり、許可する操作を増やす指示にはしない
依頼には成果、参照先、制約、完了条件を残し、認証情報や不要な個人情報は含めない

Jira AutomationからGitHub Actionsを起動し、Codexへ処理を渡す方式は選択肢の1つである
必要な書き込み権限は、イベントを送る処理、調査する処理、成果物を保存する処理に分けて決める
調査エージェントへ、すべての接続先の書き込み権限を渡す構成にはしない
[Issueから提案書を作る既存の例](issue-to-proposal-workflow.md)は、調査とGitHubへの反映を別のジョブへ分けている

「Jiraへの公式接続がない」とは一括しない
2026年10月19日の公式資料では、Codex SecurityがAtlassian Rovo経由でJiraを読み、権限と承認のもとで課題を作成または更新する例がある
これは任意のJiraイベントが自動でCodexの実装タスクを起動することとは別の接続である

## 実行場所と権限を分ける

予定タスクには、ローカルプロジェクト、Web側のタスク、クラウドで動くTeam Tasksがあり、利用面と接続条件が異なる
ローカルファイルを使う場合はPCとアプリの稼働が必要だが、すべての定期処理をローカル限定とはしない
詳しい接続と稼働条件は[外部接続とスケジュール](codex-connections-and-schedules.md)で確認する

ファイルの読み書きとネットワークは別の権限である
read-onlyと通信許可リストを組み合わせる例もあるため、sandbox名だけから通信の可否を決めない
MCP、接続済みApp、ブラウザ、Computer Useにも同じ通信制約が自動で適用されるとは仮定しない
Full AccessへRulesを足しても、OSによるファイルと通信の制限と同じ境界にはならない

`approval_policy = "never"`は、範囲外の操作へ承認を求めない設定であり、あらゆる操作を許可する設定ではない
予定タスクは、組織が許す場合にこの方針を使い、許さない場合は選択した権限モードの承認方針へ戻る
実行に必要な権限が不足した場合は、結果へ未実施の理由を残し、勝手に権限を広げない

## CI失敗を調査する

1. リポジトリ、PR、対象コミット、workflowのrun、job、試行番号を固定する
2. 失敗ログ、既存の検証手順、関連差分を読み、事実、原因候補、反証、未確認事項を分ける
3. 人が根拠を確認できる提案書を作り、原因の確定と修正の採否は別に判断する
4. 投稿が許可されている場合だけ、PRへの報告や通知へ進み、作成したコメントなどの参照先を記録する

失敗した実行を識別するキーと、通知をまとめるキーは分ける
たとえばrunとjobと試行番号で観測を区別し、同じコミットの同じ失敗が続く場合は既存の報告を更新するか、通知を省くかを決める
投稿の成否が不明なら既存の投稿を照合し、同じ内容をそのまま再送しない
ログを取得できなかったことを、コードに不具合がある証拠にはしない

## 工程を進める条件を決める

| ゲート | 確認する証拠 | 人が判断すること |
|---|---|---|
| IssueとPRの前提 | 要求、制約、参照先、変更範囲 | 今回のスコープで進めてよいか |
| 人の差分レビュー | 実装と既存設計、互換性、保守性 | 変更を受け入れるか |
| AIの一次コードレビュー | 指摘の根拠と、修正後の差分 | どの指摘を採用するか |
| CIとテスト | 要求を確認するテストと実行結果 | 観測する挙動が適切か |
| ドキュメント | 変更した仕様、運用、判断理由 | 読者と運用担当者に説明が足りるか |
| セキュリティ | 権限、シークレット、依存関係と影響 | 許容するリスクの範囲か |
| 最終承認 | 残る問題と検証結果 | マージ、公開、リリースを進めるか |

Auto-reviewはsandbox境界の承認要求を別のレビュー担当へ渡す機能であり、この表の一次コードレビューではない
すべてのゲートを毎回人手で確認する設計にはせず、機械で判定できる検査と、影響や曖昧さを人が判断する箇所を分ける
人が関わる深さを変えても、既存の必須検査、承認規則、満たすべき条件は保つ
テストの成功だけで合格にせず、既存のassertを緩めたり、skipを追加したりした差分も確認する
判定条件を下げて成功させる変更と、仕様に合わせて正当な理由でテストを直す変更を区別する

## 指標の定義をそろえる

| 指標 | 定義に必要な情報 | 欠けたときの扱い |
|---|---|---|
| サイクルタイム | Issue着手と対応するPRのマージ時刻 | PR作成時刻で代替せず、別指標か未計測にする |
| レビュー待ち | レビュー可能になった時刻と、対象とする応答の時刻 | draft期間やbotの反応を含めるかを決める |
| マージ後の修正とrevert | 観測期間内の修正、原因となるPR、分母の対象PR | 追跡期間が足りないものを区別する |
| 同じタスクの再依頼 | 同じタスクの識別子と、再依頼に数える条件 | 別要求や単なる補足を混ぜない |

期間、分母、欠測、進行中の作業を記録し、同じ条件で比較する
行数やPR数の増加を、そのまま顧客価値や品質向上へ置き換えない
GitHub、Issue管理、CIから取れる情報を使うが、イベントの定義がない状態で集計コードだけを先に作らない
少数の試行や前後比較だけから、AIが改善を引き起こしたと結論づけない

## 振り返りを規則へ戻す

[振り返りの雛形](../templates/codex-team/retrospective.md)へ、起きたこと、元の依頼、見逃した検証、再発防止案を残す
常時必要な方針は`AGENTS.md`、再利用する手順はSkill、技術的な制御はRulesやCIへ分ける
追記することだけを目的にせず、重複、古い前提、今回だけの例外は整理する
規則を変えたら、次の対象で同じ問題を検出または回避できたかを確認する

`AGENTS.override.md`は同じ階層の`AGENTS.md`へ追記されるファイルではなく、代わりに選ばれるファイルである
一時例外を書く場合も、通常の指示が読まれなくなる範囲と、解除する時期を確認する
個人用の既定の場所は`~/.codex/AGENTS.md`であり、`/.codex/AGENTS.md`とは異なる
