# Codex実行中の介入と委任

[タスク設計](task-design.md)で成果と完了条件を決めても、実装中に新しい情報が見つかることはある
介入する目的は作業を細かく指揮することではなく、前提の誤りや危険な方向を早い段階で正すことにある

## 実行中の入力を分ける

Codex CLIの現在の案内では、実行中のTabは次ターンへの入力を予約し、Enterは進行中ターンへ指示を追加する
Escは実行中画面で中断キーとして表示される場合に使う
キー割り当てと入力状態は環境で異なりうるので、実際の画面表示を確認する

| 状況 | 操作 | 例 |
| --- | --- | --- |
| 今の作業が終わった後に続ける | Tabでキューへ入れる | 実装後に対象テストの結果を報告する |
| 今の実装判断に必要な前提を補う | Enterで進行中ターンへ渡す | 保存先は既存のUserPreferencesを使う |
| 間違った変更を止める必要がある | 実行中画面の中断操作を使う | 禁止した依存関係の追加を止める |

まだ結果を見なければ決められない別機能の実装は、先回りしてキューに積まない
Enterで無関係な新規タスクを追加すると、現在のGoalと完了条件が曖昧になる
小さな書式の違いまで毎回止めず、戻しにくい変更や明らかな制約違反で中断する

## 介入からタスク設計を直す

同じ補足を繰り返すなら、次回のIssueや依頼のどこに不足があったかを確かめる

| 繰り返す補足 | 見直す場所 |
| --- | --- |
| 新しい依存関係は追加しない | Constraints |
| 既存の保存先や関数を使う | Context PointersとConstraints |
| 対象のテスト結果を示す | Done Whenと報告形式 |
| 作業範囲が広がり続ける | GoalとIssueの分割 |

介入回数が多い原因は依頼だけとは限らない
既存テストの不足、実行環境の失敗、ライブラリの挙動も切り分けてから次の依頼を直す

## 委任できる状態を作る

開発者は実装の各行を指定する代わりに、変更の目的、守る境界、完了の証拠を用意する
エージェントがテスト、lint、型チェック、ログ、既存仕様へアクセスできれば、自分の変更を確かめながら進められる
確認できない外部APIや人間の評価はDone Whenで分け、未確認のまま成功と報告させない

たとえばUIの文言なら、エージェントに候補と文体上の根拠を出させ、人間が採用案を決める
APIの不具合なら、再現条件と期待する応答を指定し、エージェントが修正前後の挙動を検証する
委任の深さはモデルの能力だけでなく、結果をどこまで観測できるかにも左右される
