# サードパーティスキルの供給形態と設計パターン

Notion / Firecrawl / Playwright の 3 つを実際に導入して比較した記録。
2026-08-25 に手元で検証した。

Agent Skills そのものの仕組みは [agent-skills.md](agent-skills.md) を参照。
この文書は「他社が配布するスキルをどう受け取るか」に絞る。

## 3 つの供給形態

スキルは単体では動かない。必ず何らかの道具とセットで配られる。
その道具が MCP サーバーなのか、ローカル CLI なのかで、導入手順と失敗の仕方が変わる。

| | Notion | Firecrawl | Playwright |
|---|---|---|---|
| 道具 | MCP サーバー（HTTP） | ローカル CLI（npm） | ローカル CLI（npm） |
| 認証 | OAuth | API キー or ブラウザ OAuth | 不要 |
| 課金 | ワークスペースのプラン | クレジット従量 | なし |
| 配布形式 | Claude Code プラグイン | `firecrawl-cli init --skills` | `playwright-cli install --skills` |
| オフライン | 不可 | 不可 | 可 |

Playwright だけ認証も課金もない。ローカルのブラウザエンジンを動かすだけだからで、
導入コストが最も低い。試すならここから始めるのが速い。

## スキルの厚みが 3 段階ある

同じ「スキル」でも、中に入っている知識の量がまったく違う。
これが実は一番重要な違いになる。

| 厚み | 例 | SKILL.md の中身 | 置き換わるもの |
|---|---|---|---|
| 薄い（コマンド辞書） | Playwright | CLI コマンドの一覧と使用例 | man ページ |
| 中（手段選択のポリシー） | Firecrawl | どの手段まで段階を上げるかの判断基準 | 熟練者の勘 |
| 厚い（業務ワークフロー） | Notion | 何をどの順に検索し、何を作り、どこに繋ぐか | 手順書 |

Playwright の SKILL.md には「ブラウザをどう操作するか」しか書いていない。
ドメイン知識が無いぶん、リサーチ用・E2E テスト用・スクレイピング用に派生させる土台として使える。

Firecrawl は逆に、判断基準が本体になる。

```
Search → Scrape → Map + Scrape → Crawl → Interact
```

安い手段から順に試す。クレジット従量課金なので、手段の選択がそのままコストになる。
この段階設計が無いと、いきなり crawl して残高を溶かす。

Notion は最も厚い。`meeting-intelligence` を動かすと `notion-search` が 3 回呼ばれる。

```
"プロジェクト定例"            固有名で引く
"プロジェクト 進捗 ステータス"  状態で引く
"meeting notes 議事録"        記録の型で引く
```

同じ道具を 3 つの切り口で叩いている。固有名だけでは過去の議事録が引っかからないので、
網を変えて広げる。この「何をどの順に検索するか」は MCP 側には無い知識になる。

## 共通する設計パターン 3 つ

厚みが違っても、よくできたスキルは同じ工夫を持っている。

### 出力をファイルに逃がす

Firecrawl は結果を `.firecrawl/` に保存し、エージェントにはパスだけ渡す。
24 記事を全部コンテキストに載せると溢れるため、grep と部分読みで処理させる。

同じ問題は自作のスキルでも起きる。大きな結果を返すツールを呼ぶときは、
ファイルに落としてから読む形にしておくと、後で困らない。

### 並列実行を明示する

「独立した操作は並列で実行せよ」と書いてあるから並列になる。
書かなければ 1 件ずつ順に回る。ただし後述の落とし穴がある。

### 段階的開示

Firecrawl のスキルは 28 個に分かれている。本体の `firecrawl` が入口で、
必要になった時点で `firecrawl-scrape` や `firecrawl-monitor` に降りる。
全部を最初に読ませない。

## 落とし穴

### プラグインのスキルは階層が 1 段ずれると無言で消える

Claude Code のスキル探索は `skills/<name>/SKILL.md` を見る。
公式の Notion プラグインは `skills/notion/<name>/SKILL.md` と 1 段深く、4 つのスキルが読み込まれなかった。

エラーも警告も出ない。`/plugin` の Installed タブは「インストールできた」しか教えない。
**インストール成功と読み込み成功は別物**で、確認方法は再起動後にスキル一覧へ実際に名前が出るかを見ることだけになる。

回避策はスキル本体を `~/.claude/skills/` へコピーすること。
frontmatter の `name` をディレクトリ名に揃えれば動く。

```bash
cp -R <plugin>/skills/<vendor>/<skill> ~/.claude/skills/<vendor>-<skill>
# SKILL.md の name: を <vendor>-<skill> に書き換える
```

### 並列実行でバックグラウンドジョブが stdin を食う

スキルの指示どおり `&` で並列化すると、次の形で静かに壊れる。

```bash
# 壊れる: バックグラウンドの子プロセスが親と同じ stdin を読んでループ入力を吸う
while read -r url; do
  some-cli scrape "$url" -o "out/$(basename "$url").md" &
done < urls.txt

# 直し方
while read -r url; do
  some-cli scrape "$url" -o "out/$(basename "$url").md" </dev/null &
done < urls.txt
```

24 件のうち 9 件しか処理されず、しかもエラーは出ない。
並列実行を促すスキルを使うときは、この形を先に潰しておく。

### xargs は置換後の長さで落ちる

```
xargs: command line cannot be assembled, too long
```

`-I{}` と `sh -c` を組み合わせると、置換後のコマンドが上限を超える。
シェルループに切り替えるほうが確実になる。

### 無料枠の制約は文書に載っていないことがある

Firecrawl の公式ドキュメントの実行例は Credits 500,000 / 並列 100 だった。
実際の無料枠は Credits 1,000 / 並列 2 で、さらに分あたりのリクエスト上限がある。

24 記事の取得で 5 件が弾かれた。

```
please retry after 23s
```

「一括で並列取得」を前提にした手順は、無料枠ではそのまま動かない。
待ち時間を挟む形に書き換える必要がある。

## 導入時の確認手順

どのスキルでも同じ順で確かめる。

1. CLI やサーバーが入ったか（`which`、`--status`、`--version`）
2. 認証が通ったか
3. **再起動後にスキル一覧へ名前が出るか**
4. 最小の 1 コマンドが通るか
5. 出力先が `.gitignore` されているか

5 は見落としやすい。Firecrawl は `.firecrawl/` に外部サイトの中身を吐くので、
塞いでいないとコミット候補に並ぶ。CLI 自身が `--status` で
`.gitignore: present - .firecrawl ignored: yes` と表示するのは良い設計だった。

## 自作スキルへ持ち帰るもの

- 手段が複数あるなら、安い順に試す段階を SKILL.md に書く
- 大きな出力はファイルに逃がし、パスだけ渡す
- 並列化を促すなら stdin の扱いまで書く
- スキルを分割し、入口から必要な分だけ降りられるようにする
- 導入手順に「読み込まれたことの確認方法」を書く
