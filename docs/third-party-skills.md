# サードパーティスキルの供給形態と設計パターン

Notion / Firecrawl / Playwright の 3 つを実際に導入して比較した記録。
2026-08-25 に手元で検証した。

Agent Skills そのものの仕組みは [agent-skills.md](agent-skills.md) を参照。
この文書は「他社が配布するスキルをどう受け取るか」に絞る。

## 3 つの供給形態

スキルは単体では動かない。必ず何らかの道具とセットで配られる。
その道具が MCP サーバーなのか、ローカル CLI なのかで、導入手順と失敗の仕方が変わる。

| | Notion | Firecrawl | Playwright | Remotion |
|---|---|---|---|---|
| 道具 | MCP サーバー（HTTP） | ローカル CLI（npm） | ローカル CLI（npm） | **なし** |
| 認証 | OAuth | API キー or ブラウザ OAuth | 不要 | 不要 |
| 課金 | ワークスペースのプラン | クレジット従量 | なし | なし |
| 配布形式 | Claude Code プラグイン | `firecrawl-cli init --skills` | `playwright-cli install --skills` | `npx skills add remotion-dev/skills` |
| オフライン | 不可 | 不可 | 可 | 可 |

Remotion には道具が付いてこない。271 ファイルすべてが Markdown で、`scripts/` が 1 つも無い。
何かを実行させるのではなく、正しい書き方を教えることに全振りしている。

Playwright は認証も課金もない。ローカルのブラウザエンジンを動かすだけなので、
導入コストが最も低い。試すならここから始めるのが速い。

## スキルの厚みが 3 段階ある

同じ「スキル」でも、中に入っている知識の量がまったく違う。
これが実は一番重要な違いになる。

| 厚み | 例 | SKILL.md の中身 | 置き換わるもの | 道具 |
|---|---|---|---|---|
| 薄い（コマンド辞書） | Playwright | CLI コマンドの一覧と使用例 | man ページ | あり |
| 中（手段選択のポリシー） | Firecrawl | どの手段まで段階を上げるかの判断基準 | 熟練者の勘 | あり |
| 厚い（業務ワークフロー） | Notion | 何をどの順に検索し、何を作り、どこに繋ぐか | 手順書 | あり |
| 厚い（API 知識の丸ごと） | Remotion | フレームワークの書き方と禁止事項 | 公式ドキュメント全体 | **なし** |

道具の有無と知識の厚みは独立している。Remotion は道具を持たずに知識だけが厚い。
Agent Skills は「指示・スクリプト・リソース」の 3 要素で組めるが、
Remotion は指示とリソースだけで成立している。

Playwright の SKILL.md には「ブラウザをどう操作するか」しか書いていない。
ドメイン知識が無いぶん、リサーチ用・E2E テスト用・スクレイピング用に派生させる土台として使える。

Firecrawl は逆に、判断基準が本体になる。

```
Search → Scrape → Map + Scrape → Crawl → Interact
```

安い手段から順に試す。クレジット従量課金なので、手段の選択がそのままコストになる。
この段階設計が無いと、いきなり crawl して残高を溶かす。

Notion は最も厚い。`meeting-intelligence` を動かすと `notion-search` が 3 回呼ばれる。

```
"プロジェクト定例"            固有名で引く
"プロジェクト 進捗 ステータス"  状態で引く
"meeting notes 議事録"        記録の型で引く
```

同じ道具を 3 つの切り口で叩いている。固有名だけでは過去の議事録が引っかからないので、
網を変えて広げる。この「何をどの順に検索するか」は MCP 側には無い知識になる。

## 共通する設計パターン 3 つ

厚みが違っても、よくできたスキルは同じ工夫を持っている。

### 出力をファイルに逃がす

Firecrawl は結果を `.firecrawl/` に保存し、エージェントにはパスだけ渡す。
24 記事を全部コンテキストに載せると溢れるため、grep と部分読みで処理させる。

同じ問題は自作のスキルでも起きる。大きな結果を返すツールを呼ぶときは、
ファイルに落としてから読む形にしておくと、後で困らない。

### 並列実行を明示する

「独立した操作は並列で実行せよ」と書いてあるから並列になる。
書かなければ 1 件ずつ順に回る。ただし後述の落とし穴がある。

### 段階的開示

Firecrawl のスキルは 28 個に分かれている。本体の `firecrawl` が入口で、
必要になった時点で `firecrawl-scrape` や `firecrawl-monitor` に降りる。
全部を最初に読ませない。

Remotion はこれをさらに徹底していて、**4 層**になっている。

```
1. スキルの選択        remotion-best-practices（description が "Router for all Remotion skills"）
2. SKILL.md            どのリファレンスを読むかの案内だけ
3. 参照ファイル        remotion-create/REFERENCE.md など
4. 相互参照            video-layout.md、multi-scene-video.md など
```

30 秒の解説動画を 1 本作ったとき、11 個のリファレンスのうち実際に読んだのは 3 個だった。
271 ファイルを全部読めば数十万トークンになる。入口を薄く保つ設計が効いている。

## 落とし穴

### プラグインのスキルは階層が 1 段ずれると無言で消える

Claude Code のスキル探索は `skills/<name>/SKILL.md` を見る。
公式の Notion プラグインは `skills/notion/<name>/SKILL.md` と 1 段深く、4 つのスキルが読み込まれなかった。

エラーも警告も出ない。`/plugin` の Installed タブは「インストールできた」しか教えない。
**インストール成功と読み込み成功は別物**で、確認方法は再起動後にスキル一覧へ実際に名前が出るかを見ることだけになる。

回避策はスキル本体を `~/.claude/skills/` へコピーすること。
frontmatter の `name` をディレクトリ名に揃えれば動く。

```bash
cp -R <plugin>/skills/<vendor>/<skill> ~/.claude/skills/<vendor>-<skill>
# SKILL.md の name: を <vendor>-<skill> に書き換える
```

### 並列実行でバックグラウンドジョブが stdin を食う

スキルの指示どおり `&` で並列化すると、次の形で静かに壊れる。

```bash
# 壊れる: バックグラウンドの子プロセスが親と同じ stdin を読んでループ入力を吸う
while read -r url; do
  some-cli scrape "$url" -o "out/$(basename "$url").md" &
done < urls.txt

# 直し方
while read -r url; do
  some-cli scrape "$url" -o "out/$(basename "$url").md" </dev/null &
done < urls.txt
```

24 件のうち 9 件しか処理されず、しかもエラーは出ない。
並列実行を促すスキルを使うときは、この形を先に潰しておく。

### xargs は置換後の長さで落ちる

```
xargs: command line cannot be assembled, too long
```

`-I{}` と `sh -c` を組み合わせると、置換後のコマンドが上限を超える。
シェルループに切り替えるほうが確実になる。

### 無料枠の制約は文書に載っていないことがある

Firecrawl の公式ドキュメントの実行例は Credits 500,000 / 並列 100 だった。
実際の無料枠は Credits 1,000 / 並列 2 で、さらに分あたりのリクエスト上限がある。

24 記事の取得で 5 件が弾かれた。

```
please retry after 23s
```

「一括で並列取得」を前提にした手順は、無料枠ではそのまま動かない。
待ち時間を挟む形に書き換える必要がある。

### 生成物は型チェックを通っても壊れている

Remotion で動画を作ったとき、`tsc --noEmit` が通ったうえで 2 シーンが壊れていた。

- カラムの中身の合計高が領域を超え、画面外へ流出した
- SVG の `viewBox` とコンテナ実寸が一致せず、接続線が繋がらず斜めに飛んだ

どちらも型では検出できない。`remotion still --frame=N` で数枚抜いて目で見るまで気づけなかった。
SKILL.md にはこの確認手順が書かれていない。

出力が視覚物・音声・長文であるスキルを使うときは、**成果物を実際に開いて確認する手順**を
自分側の手順として持っておく必要がある。

## 導入時の確認手順

どのスキルでも同じ順で確かめる。

1. CLI やサーバーが入ったか（`which`、`--status`、`--version`）
2. 認証が通ったか
3. **再起動後にスキル一覧へ名前が出るか**
4. 最小の 1 コマンドが通るか
5. 出力先が `.gitignore` されているか

5 は見落としやすい。Firecrawl は `.firecrawl/` に外部サイトの中身を吐くので、
塞いでいないとコミット候補に並ぶ。CLI 自身が `--status` で
`.gitignore: present - .firecrawl ignored: yes` と表示するのは良い設計だった。

## 自作スキルへ持ち帰るもの

- 手段が複数あるなら、安い順に試す段階を SKILL.md に書く
- 大きな出力はファイルに逃がし、パスだけ渡す
- 並列化を促すなら stdin の扱いまで書く
- スキルを分割し、入口から必要な分だけ降りられるようにする
- 導入手順に「読み込まれたことの確認方法」を書く

## スキルの探し方

skills.sh（Vercel）が配布のディレクトリとして事実上の標準になりつつある。
2026-03 時点で 87,000 を超えるスキルが登録され、20 以上のエージェントに対応する。

ポータル側で検索・リーダーボード・カテゴリ閲覧ができ、CLI 側で導入から更新までを扱う。

| コマンド | 用途 |
|---|---|
| `skills add` | 導入 |
| `skills update` | 更新 |
| `skills remove` | 削除 |
| `skills find` | 検索 |
| `skills list` | 一覧 |

`find-skills`（vercel-labs）を入れると、エージェント自身がディレクトリを検索して候補を出す。
内部では `npx skills find <keyword>` が動き、英語キーワードで引く。

```bash
npx skills add https://github.com/vercel-labs/skills --skill find-skills
```

87,000 から手作業で探す必要は無くなるが、**提案されたものをそのまま入れてよいことにはならない**。

## 信頼できるスキルの見分け方

サードパーティスキルは誰でも公開できる。名前や説明文で安全性は判断できない。

### 名前で判断できないもの

- スキル名が信頼できそうに見える
- 説明文が丁寧
- README が充実している
- タグやカテゴリが適切

これらは全部、誰でも書ける。悪意のあるスキルが信頼できそうな名前で公開される余地がある。

### 偽装しにくいもので判断する

| 観点 | 確認方法 |
|---|---|
| 提供元が公式か | そのツールやサービスの開発元が公開しているか |
| 導入実績 | 導入件数が十分か（目安として 1 万件以上） |
| セキュリティ監査 | skills.sh の Security Audits の結果 |

公式とは、Remotion なら `remotion-dev`、Playwright なら `microsoft` のように、
そのツールの提供元そのものを指す。skills.sh の Official カテゴリでも確認できる。

### Security Audits の 3 つ

skills.sh は各スキルのページに 3 種類の監査結果を出す。観点が異なる。

| ツール | 検査対象 | PASS の意味 | WARN / FAIL の意味 |
|---|---|---|---|
| Gen Agent Trust Hub | 悪意ある振る舞い（データ窃取、不審な外部通信、悪意あるコードパターン） | 危険な振る舞いが検出されなかった | 不審な動作パターンが見つかった |
| Socket | サプライチェーンリスク（依存パッケージ、なりすまし、悪意あるコードの混入） | 依存関係に問題がなかった | 依存パッケージにリスクがある |
| Snyk | ToxicSkills フレームワークの 8 カテゴリ（プロンプトインジェクション、認証情報の扱い、第三者コンテンツ露出など） | 問題が検出されなかった | 低から中リスクの問題が見つかった |

3 つとも PASS なら安心度は高い。1 つでも WARN や FAIL があれば内容を読んでから決める。

WARN が即座に危険を意味するわけではない。
リーダーボード 1 位の `find-skills` でも Snyk が WARN を出す。

```
RISK LEVEL: MEDIUM
Third-party content exposure detected
```

これは find-skills が skills.sh のレジストリや GitHub を検索する性質上、
信頼されていない外部コンテンツを扱う可能性があるという指摘になる。機能そのものに由来する。

**WARN の内容を読んでリスクを理解したうえで判断する**、が正しい扱い方になる。

### スクリプトの有無で危険度が変わる

SKILL.md だけのスキルはエージェントへの指示にすぎないので、相対的に安全になる。
シェルスクリプトや Python スクリプトを実行するスキルは、ファイル削除や外部送信のリスクを持つ。

この観点で見ると、前掲の 4 つのうち Remotion が最も安全側に寄る。271 ファイルすべてが Markdown で、
実行するものが 1 つも無い。逆に CLI を伴うものは、その CLI 自体が信頼の対象になる。

## 公式でも供給元は確かめる

実例がある。ある公式プラグインの導入手順が、
公式リポジトリではなく**個人のフォーク**を指していた。

```
本文の記載     github.com/<vendor>/<plugin>
実行コマンド   /plugin marketplace add <個人>/<plugin>
```

フォークの差分を調べると 2 コミットだけで、SKILL.md の中身は `+0/-0` の変更なし。
ディレクトリ移動と、marketplace.json の参照先を自分のフォークに向ける 1 行だった。

```diff
-          "repo": "<vendor>/<plugin>"
+          "repo": "<個人>/<plugin>"
```

悪意は見当たらず、公式の階層では読み込まれない問題を直すための実用的なフォークだった。
それでも公式を使うべき理由が 2 つある。

第 1 に、フォークは upstream の更新に追従しない。提供元がスキルを直しても反映されない。
第 2 に、プラグインの導入はスキル定義と接続設定をそのまま取り込むため、供給元は少ないほうがよい。

**マーケットプレイスの追加先は 1 行で変わる。** レビューで見落としやすい箇所になる。
チームにスキルを配る立場なら、供給元をどこにするかが実質的な権限委譲にあたる。

## 判断に迷ったら自作する

提供元・導入実績・監査結果のいずれかで不審な点があれば、入れずに自作するのが最も安全になる。
スキルは Markdown とディレクトリだけで書けるため、自作の初期コストは高くない。
