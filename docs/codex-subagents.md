# Codex のサブエージェント

サブエージェントは、作業を増やすための機能ではなく、文脈を分けるための機能として使う
メインエージェントは全体の方針と最終判断を持ち、サブエージェントには範囲を絞った調査、レビュー、比較を任せて、判断の材料だけを返させる

Claude Code のサブエージェントは [subagents.md](subagents.md)、スキルとの違いは [agent-skills.md](agent-skills.md) にある

## メインとサブの分担

| 観点 | メインエージェント | サブエージェント |
| --- | --- | --- |
| 役割 | 利用者との対話、全体の方針、最終判断 | 範囲を絞った調査、レビュー、実装 |
| 扱う情報 | 会話全体、利用者の意図 | 指定されたファイル、ログ、テスト |
| 結果 | 最終の回答 | メインに返す |

流れは「利用者 → メイン → サブ → メイン → 利用者」
最終判断をサブに任せると、判断に要る文脈を大量に渡すことになり、渡さなかった文脈は判断から抜け落ちる。判断はメインに残す

## いつ起動されるか

次のどれかがあると起動しやすい。ただし必ず起動するわけではなく、Codex の判断も入る

- 依頼の中で、委譲や並列の作業を明示する
- AGENTS.md やスキルに、委譲の指示を書く
- reasoning effort を extra high にする

「調べて」だけの軽い依頼では起動しないことがあり、逆に複雑な依頼では明示しなくても起動することがある

## 分け方の 3 つの軸

| 軸 | 中身 | 例 |
| --- | --- | --- |
| 作業を分ける | 範囲を分担して並列に進める | API、画面、テストの調査を別々に |
| 文脈を分ける | メインの経緯を知らない状態で判断させる | 実装の後、変更したファイルだけを読ませてレビューさせる |
| 観点を分ける | 同じ成果物を別々の観点で見る | 仕様との整合、テスト不足、セキュリティ、読みやすさ |

- 文脈を分ける軸は、直列に動かしても意味がある。メインには、実装中の迷い、妥協、捨てた案が残っていて、レビューがそれに引っ張られる。成果物と観点だけを渡せば、経緯から切り離した判断が返る
- 3 つは組み合わせてよい。サブエージェントを使うこと自体を目的にしない
- 任せるのは単純作業に限らない。比較、評価、リスクの整理、複数案の検討も任せられる。決めるのは「何を任せるか」より「何を判断させ、何を返させるか」

## 依頼の書き方

決まった書式はないが、大きな依頼では次の 4 つを書くと安定する

```text
Goal: ログイン画面の改修の影響を調べる
Context Pointers: ログイン画面の実装、認証の処理、関連するテスト、仕様メモ
Constraints: 上の 4 か所だけを読む。ファイルを変更しない。推測で原因を断定しない
Done When: 入力チェック、エラー表示、認証 API の呼び出し、既存テストの範囲が箇条書きになっている。影響するファイルのパスがある
```

戻り値の形も決める。要約、ファイルパスの一覧、変更の候補、確かめられなかったこと、のようにメインが統合しやすい形にする

## 始め方と数

- まず読み取り中心の作業から始める。限られた範囲の調査、原因や設計案のレビュー、テストの失敗の原因、大きな変更の前の影響範囲
- 複数のサブエージェントに同じ領域を同時に編集させると、差分や方針がぶつかる
- 数を増やすほど、トークン、待ち時間、メインの統合の手間が増える

| 設定 | 中身 | 既定 |
| --- | --- | --- |
| `agents.max_threads` | 同時に開ける agent の数。今は `agents.max_concurrent_threads_per_session` の古い別名 | 6 |
| `agents.max_depth` | サブがさらにサブを起動できる深さ。根を 0 と数え、1 なら孫は起動できない | 1 |

## カスタムエージェント

役割ごとに、読み書きの範囲とモデルを分けられる
個人用は `~/.codex/agents/`、プロジェクト用は `.codex/agents/` に、1 つのエージェントにつき 1 つの TOML を置く

| キー | 必須 | 中身 |
| --- | --- | --- |
| `name` | はい | エージェントの名前 |
| `description` | はい | いつ使うか。スキルの description と同じく、選ばれるかを左右する |
| `developer_instructions` | はい | 振る舞いの指示 |
| `sandbox_mode`、`model`、`model_reasoning_effort` など | いいえ | 省くと親の設定を引き継ぐ |

組み込みのエージェントは `default`（汎用）、`explorer`（探索と調査）、`worker`（編集、実装、テストの修正）

このリポジトリでは、読み取り専用の 2 つを [codex/agents/](../codex/agents/) に置いている

| 名前 | 役割 | 分け方の軸 |
| --- | --- | --- |
| researcher | 範囲を絞って調べ、事実と根拠のパス、確かめられなかったことを返す | 作業を分ける |
| reviewer | 経緯を知らない立場で、指定された観点だけからレビューする | 文脈と観点を分ける |

入れ方は `codex/install.sh`。スキルはシンボリックリンクで張り、カスタムエージェントは複製する

### 確かめたこと（codex-cli 0.160.0、2026-10-03）

- カスタムエージェントの TOML をシンボリックリンクで置くと、`spawn_agent` が「agent type is currently not available」で失敗した。実ファイルで置くと researcher が起動し、結果を返した
- スキルはシンボリックリンクのままで読まれた（create-pr、weekly-report など）
- そのため install.sh は、エージェントだけを複製にしている。リポジトリの TOML を直したら install.sh を流し直す

## スキルとの違い

| | スキル | サブエージェント |
| --- | --- | --- |
| 何を足すか | 作業の知識を、今のコンテキストに読み込む | 別のコンテキストで作業させる |
| 効く場面 | 毎回同じ規則や手順を使う作業 | 経緯から切り離した判断、並列の調査 |
| 組み合わせ | スキルに「この作業はサブエージェントに任せる」と書けば、委譲のきっかけになる | サブエージェントもスキルを読める |
