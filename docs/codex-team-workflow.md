# チームでCodexへ任せる作業と品質ゲートを決める

同じエージェントを使っても、依頼に含める制約と検証が違えば、確認できる品質の範囲はそろわない
最初に試す作業を1つ選び、エージェントへ任せること、人が確認すること、人が責任を持って決めることを分ける
結果の採否を決める担当と、困ったときの相談先も開始前に決める

## 工程ごとの役割

ソフトウェア開発ライフサイクル（SDLC）を次の工程に分ける
DelegateはAIへ任せる作業、Reviewは人が確認する作業、Ownは人が責任を持って判断する内容である

| 工程 | Delegate | Review | Own |
|---|---|---|---|
| Plan | 要求とコードの照合、影響範囲と未決事項の整理 | 前提と技術的制約の不足を確かめる | 優先順位、スコープ、順序 |
| Design | 既存設計に沿う案と部品を作る | 統合、アクセシビリティ、設計基準との整合を確かめる | 体験とアーキテクチャの方針 |
| Build | 実装、接続、変更に必要なテストを進める | 性能、セキュリティ、互換性、ドメインとの整合を確かめる | 抽象化、横断変更、保守性の判断 |
| Test | 仕様に沿うケースとテストの初稿を作る | 実行結果と、テストが実際に観測する挙動を確かめる | 正常系、境界、異常系、状態遷移を含む合格条件 |
| Review / Document | 一次レビュー、修正案、文書の更新案を作る | 差分、要求、説明の正確さと読者の前提を確かめる | 受け入れと公開範囲、運用担当者に必要な説明 |
| Deploy and Maintain | ログと指標の調査、原因候補、修正案を作る | 診断の根拠、修正と本番への影響を確かめる | リリース、重大障害、権限と許容リスク |

AIの一次レビューを通過したことと、人の受け入れは分ける
エージェントの確信度だけで本番へ進めず、要求した動作と結果の証拠を確認する

## 指示と実行制約を分ける

| 仕組み | 決める内容 | 単独では確かめられないこと |
|---|---|---|
| `AGENTS.md` | 作業方針、検証コマンド、レビュー観点 | 書いた方針が毎回実行されたこと |
| Skills | 特定作業の手順と判断基準 | 手順の適用と成果の正しさ |
| `config.toml` | 実行時の既定値 | 利用者が変更できない組織の強制条件 |
| Rules | sandbox外コマンドの引数プレフィックスに対する判定 | あらゆる経路での同じ操作の禁止 |
| CIとリポジトリのマージ条件 | 自動検査と、通過を必須とする条件 | 人が決める仕様やリスクの妥当性 |
| `requirements.toml` | 管理者が許す設定の範囲 | 対象クライアントで実際に適用されたこと |

Team Configは、設定、Rules、Skillsなどを共有する構成として扱う
既定値の共有と管理者の強制条件を同じものにしない
プロジェクトの`.codex`設定とRulesは、信頼済みの層として読み込まれる必要がある

## Rulesを狭い例で確かめる

[配布用のRules例](../templates/codex-team/rules/command-review.rules)は、マージの確認と、特定の削除コマンド形の拒否を示す
このリポジトリの実行規則として自動で導入する配置ではない

Rulesが複数一致すると、`forbidden`、`prompt`、`allow`の順で厳しい判定が採用される
ただし、引数の順番やラッパーが変わると、同じ操作でも同じプレフィックスに一致しないことがある
複雑なシェル構文は個々のコマンドへ分割されず、シェル全体の呼び出しとして判定される場合もある
`rm -rf`の規則を置いただけで、すべての削除が禁止されたとは判断しない

`codex execpolicy check`へ規則と対象コマンドの引数を渡すと、コマンドを実行せず判定を確認できる
一致例、非一致例、規則なしの対照を比べ、何を制御したかを確認する
判定ツールの結果と、プロジェクトで規則が読み込まれたことや、実行時の制御は別に確認する

`codex-cli 0.162.0`の判定ツールでは、同じ引数を次の条件で比較した
対象のマージや削除コマンドは実行していない

| 判定対象 | 配布用の規則 | 規則なし | 許可する対照規則と併用 |
|---|---|---|---|
| `gh pr merge 42` | `prompt` | 一致する規則なし | `prompt` |
| `rm -rf example-output` | `forbidden` | 一致する規則なし | `forbidden` |

`rm -fr`、`rm -r -f`、`gh pr --repo example/project merge 42`は、この例の規則には一致しなかった
非一致の出力に許可判定はなく、その結果を実行許可とは扱わない

## 設定を共有するときの確認

2026年10月18日に確認した公式資料では、教材の例に次の修正が必要である

| 項目 | 現行資料の読み方 |
|---|---|
| `approval_policy = "untrusted"` | 明示設定は廃止。プロジェクトの`trust_level`や管理者側の許容値とは別の話である |
| `approval_policy = "never"` | 承認プロンプトを無効にする設定であり、sandbox解除と同義ではない |
| `approvals_reviewer` | `user`か`auto_review`を選ぶ。自動レビューを選んでもsandboxの範囲は広がらない |
| 名前付き権限プロファイル | `[permissions.<name>.filesystem]`などに定義し、`default_permissions`で選ぶ。legacyのsandbox設定と混在させない |
| `[permissions.filesystem]` | 管理者要件の共通読み取り拒否に使う予約領域で、名前付きプロファイルの定義とは異なる |

管理者のコマンド規則は許可を追加する仕組みではなく、`prompt`または`forbidden`で制約する
要件違反時の通知、互換値への調整、拒否は設定の種類によって異なるため、一律の挙動を前提にしない
配布前に利用するクライアントのバージョンで確かめ、管理者設定の導入は通常のチーム手順とは分ける

## 小さな作業で運用を試す

最初はIssueの読み解き、変更の説明、テスト失敗の調査、文書の更新漏れ確認など、結果を見て判断できる作業を選ぶ
[作業分担の雛形](../templates/codex-team/task-ownership.md)へ、任せる範囲、採否を決める人、相談先、品質ゲートを記入する
並行作業は変更する範囲と検証を分け、競合した場合はどの担当へ戻すかを決める

繰り返した手順が安定したらSkillへまとめ、実行時期も定まったらAutomationを検討する
Skillsは手順、Automationsは実行時期を持つが、結果の確認先と対応する人は両方に要る
試行後は、追加で必要だった前提、差し戻し理由、手順を変更した結果を記録へ戻す
共有Skillがあっても、品質が自動的に一定になると仮定せず、結果を同じ基準で確認する
