# Codex Plan modeの使いどころとプランレビュー

Plan modeは、編集を始める前にコードベースを調べ、実装方針を人間とそろえるために使う
小さく明確な作業へ毎回適用するものではない
複数の実装案が成立し、選択を誤ると手戻りが大きいときに価値が高い

## 使うかどうかの判断

| 依頼の状態 | 進め方 |
| --- | --- |
| 対象と変更方法が明確 | 必要な箇所を確認して実装する |
| 要件や変更範囲に未決定事項がある | Plan modeで調査し、方針を確認する |
| 認証、DB移行、公開APIなど戻しにくい変更がある | 影響範囲と移行方法を実装前にレビューする |
| 調査結果によって次の手が変わる長い作業 | 検証条件を固定し、計画を更新しながら進める |

ファイル数だけでは判断しない
1ファイルの認可変更でも事前の方針確認が要る場合があり、複数ファイルの機械的な置換なら短い依頼で足りる場合がある
調査だけの依頼は通常の会話でも扱えるが、調査から実装案を作ることが目的ならPlan modeを使える

## 調査から実装方針まで

次の3段階はPlan modeの内部状態ではなく、プランを作るための実務上の進め方である

| 段階 | エージェントが確認すること | 人間が決めること |
| --- | --- | --- |
| 関連コードを確かめる | 呼び出し経路、既存の責務、テストの入口 | 最初に調べる範囲を示す |
| 意図を合わせる | 目的、成功条件、互換性、未決定事項 | コードにない業務上の判断を補う |
| 実装方針を示す | 変更箇所、データの流れ、移行、検証順序 | 案をレビューして修正点を伝える |

最初からリポジトリ全体を読む必要はない
関係する経路から調べ、コードだけでは分からない互換性やプロダクト上の優先順位を人間との対話で補う
プランは調査時点の仮説なので、実装やテストで新しい事実が出たら更新する

エージェントが質問するのは、コードや既存資料から決められず、答えによって実装が変わる論点に絞る
認証方式の移行なら「既存セッションを切るか、期限まで継続するか」を選択肢と影響とともに示す
推奨案は根拠があるときだけ添え、未回答を承認として扱わない

## プランで確認すること

プランはファイル一覧ではなく、[タスク設計](task-design.md)の4要素を実装可能な判断へ変換したものとして読む

| 観点 | 確認すること |
| --- | --- |
| Goal | 最終的な挙動が具体的か |
| Context Pointers | 変更元と既存テストを確認したか |
| Constraints | 互換性、依存、変更禁止範囲を守れるか |
| Done When | コマンド、挙動、人間のレビューのどれで完了を判定するか |
| 影響と順序 | 変更が広がりすぎず、危険な変更の前に検証できるか |

たとえばTodoアプリに「全削除」を足すなら、既存の「完了を削除」と区別する
プランではフィルタ状態に関係なく全件を対象とし、確認ダイアログでキャンセルした場合はデータを変えないことを決める
削除を承認した場合は保存先も空にし、再読込後も0件であることを確認する
0件時のボタン状態も検証する
単一HTMLのアプリなら、関係のない検索APIや別画面の変更を制約に加えない

プランのステップ数やTest Planの項目数だけではタスクの大きさは分からない
「全削除」にキャンセル、承認、フィルタ中、再読込後、0件時の検証が並んでも、一つの操作を条件ごとに確かめている
一方、カテゴリ、検索、並び替え、期限表示をまとめたプランは独立した成果と検証を含むため、Issueや実装段階を分ける余地がある

## 計画時の推論強度

Codexの設定にはPlan mode専用の`plan_mode_reasoning_effort`がある
通常時を`medium`、Plan modeを`high`にする例は次のとおり

```toml
model_reasoning_effort = "medium"
plan_mode_reasoning_effort = "high"
```

この設定は、選択したモデルが`high`をサポートするときに有効で、Plan mode以外の通常設定は`medium`のままになる
高い推論強度は計画の正確さを保証しない
影響範囲や移行順序の判断が難しい仕事で試し、応答時間と検証後の手戻りを比べて採用する

## 操作と実装への移行

Codex CLIでは`/plan`でPlan modeへ切り替えられ、`/plan <依頼>`で切り替えと最初の依頼を同時に送れる
Codex Appでもモード切り替えから利用できる
提示されたプランの前提、変更範囲、検証方法を読み、不足があれば修正を依頼する
方針が定まったら利用している画面の操作に従って実装へ進む
プランを作ったこと自体は実装の完了を意味しない
実装中に前提が変わった場合の伝え方は[実行中の介入と委任](codex-execution-steering.md)にまとめた
