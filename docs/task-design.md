# コーディングエージェントへのタスク設計

コーディングエージェントはリポジトリを読めても、チーム内の暗黙の判断まで知っているわけではない
必要な前提が欠けると、エージェントは既存コードから推測して作業を進める
その推測が意図と違う場合、後から変更範囲を戻し、再検証する作業が増える

短い依頼が常に不足するわけではない
作業が明確なら短い指示でも進められる
複雑さや変更の影響に応じて、成果、参照先、守る条件、完了の証拠を足す

## 依頼に含める情報

OpenAIのCodex向け案内は、Goal、Context、Constraints、Done whenを依頼の基本形として挙げている
これは「Mini Codex」という製品機能ではなく、タスクを記述するための簡潔な型である

| 要素 | 決めること | 例 |
| --- | --- | --- |
| Goal | どの挙動を変えるか | 商品検索をカテゴリで絞り込めるようにする |
| Context Pointers | 判断の起点となる場所 | 検索画面、商品API、カテゴリ定義、既存仕様 |
| Constraints | 維持する挙動と変更の境界 | 既存部品を使い、カテゴリ未指定時の動作を維持する |
| Done When | 何を観測したら完了か | 選択時の絞り込みと未選択時の従来動作を確認する |

最初から四つの欄を必ず埋める必要はない
たとえば単一の誤字修正なら、対象と期待する結果だけで足りる
一方、互換性や権限に関わる変更では、制約と検証方法を省くと、動いたように見えても安全性を判断できない

たとえば「商品検索にカテゴリフィルタを付けて」だけでは、既存部品を使うか、APIに変更が必要か、未選択時に何を表示するかが分からない
次は架空のディレクトリ構成を使い、判断に必要な参照先と互換性を添えた例である

```text
Goal
商品検索画面でカテゴリを選ぶと、そのカテゴリの商品だけを表示する

Context Pointers
- 検索画面は src/screens/ProductSearch/
- 商品APIは src/api/products.ts
- カテゴリ定義は src/constants/categories.ts
- 既存仕様は README.md の Search セクション

Constraints
- 既存の FilterDropdown を使い、新しい依存関係は追加しない
- カテゴリ未指定時は従来どおり全件を表示する
- 既存APIの応答形式を維持する

Done When
- カテゴリ選択時に該当商品だけが表示されることをE2Eテストで確認する
- カテゴリ未指定時の既存テストが通る
- npm test と npm run lint が通る
```

Done Whenは「コマンドが成功した」だけでなく、求める挙動をどの証拠で確認するかまで書く
検証の方法は次の三つに分けて考えられる

| 検証の方法 | 例 | 完了判断での役割 |
| --- | --- | --- |
| コマンド | テスト、lint、ビルド | 既知の検査に失敗していないか確認する |
| 挙動 | 未ログイン時は401、カテゴリ選択時は該当商品のみ表示 | 要求そのものを満たすか確認する |
| 人間のレビュー | 文言の自然さ、画面の使いやすさ、設計判断 | 機械的に決めきれない観点を引き受ける |

コマンドがすべて通っても、要求した挙動をテストが覆っていなければ完了とは言えない
満たしていない条件があれば修正し、同じ証拠で再検証する
逆に文章やUIの仕事を無理にコマンドだけで判定する必要もない
人間が決める仕事では、候補、比較の根拠、懸念点をエージェントに出させ、最終採用を人間の判断として残す
変更内容、実行した検証、未解決事項の報告形式は、合格条件と区別して依頼に添える

## 分割する単位を決める

タスクはファイル数だけで分けない
変更後に独立して確かめられる挙動、失敗時に切り分けたい境界、レビューで求める判断を基準にする
「完了条件を一文で言えるか」は検討の手掛かりになるが、一文に収まらないことだけで分割を決めない

たとえば認証機能全体を依頼する場合、登録、ログイン、保護されたAPIへのアクセスには別の失敗条件がある
データモデルと移行を先に確かめ、登録とログインをそれぞれ動かし、最後に認証なしで拒否されることを統合テストで確認できる
ただし同じ変更と検証を共有する実装を細かく切り離すと、引き継ぎと再確認のコストが増える

| 状況 | 進め方 |
| --- | --- |
| 対象と修正方法が明確 | そのまま実装し、変更に合う検証を行う |
| 複数の設計案や依存関係がある | 実装前にPlan modeで調査と方針を確認する |
| 成果は明確だが、次の手が実験結果で変わる | 検証面と停止条件を定めてGoal modeを検討する |

Plan modeを使うかどうかはファイル数や「中規模」という名称で決めない
変更が複雑、曖昧、高リスクで、着手前の調査や合意が結果を変えるときに使う
[Plan modeの進め方](codex-plan-mode.md)では、関連コードの調査、意図の確認、実装方針のレビューを具体化する
Goal modeは一度の依頼で終わらず、計測やテストの結果を見て次の手を選ぶ作業に向く

## チームで使う基準にする

同じ作業でも、どの変更を一つのタスクやPRにまとめるかは人によって異なる
チームでは、レビューで一つの判断を下せるか、完了をどのテストや実機確認で示すかを先にそろえる
Issueを作るときは、Goal、Context Pointers、Constraints、Done Whenを本文に必要な深さで残す
一つのIssueを進めるための調査、実装、テストは作業手順として扱い、それぞれにIssueを作る必要はない
Linearでは標準のIssueテンプレートに4要素をプレースホルダーとして置けるが、チームの既定テンプレートにするかはIssueの種類を見て決める
繰り返し必要になる規約は[コンテキスト設計](context-design.md)に沿って`AGENTS.md`やSkillへ移し、今回限りの背景は依頼に残す
より大きな機能では[仕様駆動開発](spec-driven-development.md)の要求、設計、タスクへ展開する
