# コーディングエージェントへのタスク設計

コーディングエージェントはリポジトリを読めても、チーム内の暗黙の判断まで知っているわけではない
必要な前提が欠けると、エージェントは既存コードから推測して作業を進める
その推測が意図と違う場合、後から変更範囲を戻し、再検証する作業が増える

短い依頼が常に不足するわけではない
作業が明確なら短い指示でも進められる
複雑さや変更の影響に応じて、成果、参照先、守る条件、完了の証拠を足す

## 依頼に含める情報

OpenAIのCodex向け案内は、Goal、Context、Constraints、Done whenを依頼の基本形として挙げている
これは「Mini Codex」という製品機能ではなく、タスクを記述するための簡潔な型である

| 要素 | 決めること | 例 |
| --- | --- | --- |
| Goal | どの挙動を変えるか | 設定を保存した後、再読込しても値が残るようにする |
| Context Pointers | 判断の起点となる場所 | 設定画面、保存API、再現手順、既存テスト |
| Constraints | 維持する挙動と変更の境界 | APIの形式を変えず、別画面の保存処理には触れない |
| Done When | 何を観測したら完了か | 再現手順が通り、回帰テストが成功する |

```text
Goal
設定画面で保存した値が、再読込後も表示されるようにする

Context Pointers
設定画面、保存API、失敗する操作手順、既存テストを確認する

Constraints
APIの入出力形式を維持し、無関係な画面には触れない

Done When
保存後に再読込して値が残り、対象の回帰テストが通る
```

最初から四つの欄を必ず埋める必要はない
たとえば単一の誤字修正なら、対象と期待する結果だけで足りる
一方、互換性や権限に関わる変更では、制約と検証方法を省くと、動いたように見えても安全性を判断できない

## 分割する単位を決める

タスクはファイル数だけで分けない
変更後に独立して確かめられる挙動、失敗時に切り分けたい境界、レビューで求める判断を基準にする
「完了条件を一文で言えるか」は検討の手掛かりになるが、一文に収まらないことだけで分割を決めない

たとえば認証機能全体を依頼する場合、登録、ログイン、保護されたAPIへのアクセスには別の失敗条件がある
データモデルと移行を先に確かめ、登録とログインをそれぞれ動かし、最後に認証なしで拒否されることを統合テストで確認できる
ただし同じ変更と検証を共有する実装を細かく切り離すと、引き継ぎと再確認のコストが増える

| 状況 | 進め方 |
| --- | --- |
| 対象と修正方法が明確 | そのまま実装し、変更に合う検証を行う |
| 複数の設計案や依存関係がある | 実装前にPlan modeで調査と方針を確認する |
| 成果は明確だが、次の手が実験結果で変わる | 検証面と停止条件を定めてGoal modeを検討する |

Plan modeを使うかどうかはファイル数や「中規模」という名称で決めない
変更が複雑、曖昧、高リスクで、着手前の調査や合意が結果を変えるときに使う
Goal modeは一度の依頼で終わらず、計測やテストの結果を見て次の手を選ぶ作業に向く

## チームで使う基準にする

同じ作業でも、どの変更を一つのタスクやPRにまとめるかは人によって異なる
チームでは、レビューで一つの判断を下せるか、完了をどのテストや実機確認で示すかを先にそろえる
繰り返し必要になる規約は[コンテキスト設計](context-design.md)に沿って`AGENTS.md`やSkillへ移し、今回限りの背景は依頼に残す
より大きな機能では[仕様駆動開発](spec-driven-development.md)の要求、設計、タスクへ展開する
